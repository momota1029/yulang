## Requested scoped decision

Choose the construction rule that associates each actual type occurrence in an extrusion parent/copy pair with its semantic Value variable for the already-approved Value-SCC activation test. This does not reopen the graph domain, reference edges, copy-incidence rule, or the selected operation of equating the retained extrusion-related type variables when their associated Values share an SCC.

The user clarified: “型変数は値変数に結びついていて，値変数のSCCが等しくなった場合，対応する型変数がintrusionされる”. That settles the graph/type-coordinate distinction. The remaining question is which Values are associated with the two particular type occurrences and how that association moves across the extrusion boundary.

## Background and current premises

An independently reviewed proof and source audit at the baseline above checked the original Simple-sub `Typer.scala` constructors and current Yulang source-to-extrusion path. They establish the native polar pairs for:

```text
let rec f =
  let g = lambda y. f y
  in g
in f
```

The actual pairs are `(C,B,+,1)` and `(D,R,-,1)`. The approved source-reference rules give `F → G`, `G → F`, `G → Y`, and Apply-result edges from `V_R` to `F` and `Y`. Thus `F` and `G` share an SCC; `Y` and `V_R` do not share that SCC in the graph generated by these rules.

Holding the copy-side association to `F` fixed solely to isolate the missing parent rule produces different activation outcomes:

| Type pair | Immediate source operand/result association | Enclosing callable-description association |
| --- | --- | --- |
| `(C,B)` | copy `F`, parent formal Value `Y`: not same SCC | copy definition Value `F`, parent description Value `G`: same SCC |
| `(D,R)` | copy `F`, parent Apply-result Value `V_R`: not same SCC | copy `F`, parent description Value `G`: same SCC |

These are alternative candidate completions, not inferred source facts. Original Simple-sub specifies type variables, bounds, levels, extrusion and freshening, but no Yulang Value-reference graph. Current approved Yulang rules likewise do not yet specify this occurrence-level association or its extrusion transport. The solver's existing `Parent` record contains type-row endpoints, polarity and target level, not these Value witnesses.

`id x = x`, `konst x = 0`, and `f(0)(0)` were checked as controls: their sharing or Apply-reference rules do not choose the association for a wrong-level copied Function port.

## Options and consequences

1. **Immediate operand/result ownership.** Associate a type occurrence with the Value whose type is being directly supplied at that operand/result position; at extrusion, associate the copied occurrence with the receiving Value description. In the displayed construction, this gives `(F,Y)` and `(F,V_R)` and no intrusion for these pairs. It preserves the distinction between formal/result Values and the enclosing function Values.
2. **Enclosing callable-description ownership.** Associate all suboccurrences of a callable's complete inferred description with that describing function Value; when a demanded description is copied into another function's type, associate the copy with that receiving function Value. In the displayed construction, this gives `(F,G)` for both pairs and triggers `C=B` and `D=R` because `F` and `G` share an SCC.
3. **Specify another occurrence rule.** State which Value owns each side of the pair and how Function argument/result ports, reused type coordinates, polar copies, shared captures, and fresh uses preserve that association. A mixed rule is possible; it must still determine the displayed pairs.

All options retain the approved Value graph and do not copy or retarget reference incidences. They differ in when actual type equalities are imposed, so they can change inferred recursive types and require corresponding soundness/principality proofs. No option is inferred from current implementation behavior.
