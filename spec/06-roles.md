# 章6 role・method・cast

状態の凡例は [README](README.md)。この章は `role` / `impl` / `where`、`x.method` の解決、`cast` を扱う。
role の解決アルゴリズム（不変区間規則、level 管理、関連型の再帰的な解決）は仕様ではなく核の計算体系（Lean）の側で扱う。ここは利用者から見える意味だけ。

## 6.1 `role`　〔仮採用〕

```yulang
role Add 'a:
    our a.add: 'a -> 'a

role Index 'container 'key:
    type value
    our container.index: 'key -> value
```

- `role` は、型が実装できる method と、associated type（`type value`）の集まり。associated type は、role 側に default（`type value = char`）がなければ `impl` で必ず `type value = ...` と指定する。default があれば省略できる（確定, 2026-11-04）。型引数を複数持てる。
- method header `our a.add: ...` の `a` は、実装対象の型の値（receiver）を表す。
- method は default の本体を持てる（確定, 2026-11-04）。`impl` が書かなければ default が使われ、書けば上書きする。本体のない method（型 signature だけ）は `impl` が必ず書く。

```yulang
role Eq 'a:
    our a.eq: 'a -> bool
    our a.ne b = not (a.eq b)          // default の本体

impl Eq int:
    our x.eq y = ...                   // ne は書かない
```

- **receiver の無い member を書ける**（確定, 2026-11-07）。header に `a.` を付けず、`our name: 型` と書く。role の型引数は、呼び出しの**戻り値の型**で決まる（6.3 の `default ()` と同じ性質）。tagless final のように、値を作る命令を role に並べたいときに使う。
  - member の型は**必ず関数型**で、少なくとも 1 つ引数を取る。値だけの member は書けない（章3.3 の「引数なしの関数という概念は無い」と同じ。引数が要らないときは `()` を受ける）。
  - 呼び出しは companion module の名前か、`use` で入れた名前で、普通の関数として書く（`doc::text "x"`）。receiver が無いので、`x.text` の形では呼べず、6.4 の method 解決には入らない。

```yulang
role Doc 'r:
    our text: str -> 'r
    our section: str -> 'r -> 'r
    our rule: () -> 'r
```

- `role` も companion module を作る。

出典: `main:web/docs/ja/reference/structs.md` §Role

## 6.2 `impl`　〔曖昧時の扱いは確定、他は仮採用〕

```yulang
impl Add int:
    our x.add y = std::int::add x y

impl Index str int:
    type value = char
    our s.index i = std::text::str::index_raw s i
```

- `impl` は具体的な型にも、型引数を持つ一般的な型（`impl Display (list 'a)`）にも、一部の型引数だけを決めた型（`impl Display (list int)`）にも書ける（確定, 2026-11-04）。候補が重なれば曖昧エラー、重ならなければ共存する。
- **`impl` の head の `_` は、名前を付けない型変数である**（確定, 2026-11-05）。`impl Add (ref _ int)` は `impl Add (ref 'e int)` と同じ意味で、使わない変数の名前を省略した書き方になる。`_` は出現のたびに別の変数として扱う（同じ変数を二箇所に使いたいときは名前を付ける）。`where` から参照することはできない。
- role 名の直後の型が最初の型引数を埋め、後ろの型が残りを埋める。
- `impl` の中の `our` が候補として公開される。`my` は `impl` の中の helper。
- 足りない method、role にない method は検査で報告される。
- `struct` の `with:` の中にも `impl` を書ける。その場合、外側の struct が role の最初の型引数として前に足される。

```yulang
struct box 'a { value: 'a } with:
    impl Index int:
        type value = 'a
        our b.index i = b.value
```

- **`impl` は、それを含むファイルが読み込まれたときにだけ候補になる。** 読み込まれていないファイルの `impl` は、method 選択にも role の解決にも入らない。
  読み込まれた後の可視性は、通常の module の可視性（`my` / `our` / `pub`）に従う。
- 同じ role と型に対して複数の `impl` が候補になる場合は**曖昧**として拒否される（確定, 2026-11-04）。
- **`impl` の候補は、具体化した場所（呼び出し側）で見えるものから選ぶ**（確定, 2026-11-05）。`lib.yu` の `twice(x) = x.add x`（`'a: Add`）を `user.yu` で `user_id` に使うなら、`Add user_id` は `user.yu` の可視範囲で探す。見つかった `impl` の証拠は関数へ渡される。入れ子の `where`（`impl Display (list 'a)` の `'a: Display` など）も、根の呼び出し側の可視範囲で解く。定義側（`lib.yu`）からは見えない `impl` でも、呼び出し側から見えれば使える。同じ式でも、見える `impl` が違う場所では結果が変わりうる。可視性は通常の module の可視性（`my` / `our` / `pub`）に従う。
  - **グローバルな一意性（coherence）や孤児規則は課さない**（確定, 2026-11-05）。同じ role・同じ型の `impl` が別のファイルに別々にあってもよく、一つの場所に両方が見えたときだけ曖昧エラーになる。孤児規則は、必要が出てから足す（足しても既存のコードは壊れない）。値を別のファイルへ渡すとき、証拠（辞書）は具体化した側のものが渡る。

出典: `main:web/docs/ja/reference/structs.md` §impl、`main:spec/2026-06-04-method-selection.md` §impl候補の有効範囲

## 6.3 `where`　〔仮採用〕

```yulang
my twice(x: 'a) =
    where 'a: Add
    x.add x
```

- `where` は型変数に role の制約を付ける。binding・`role`・`impl` の body の中に書ける。`act` の operation の署名にも、署名の下に `where` を書ける（確定, 2026-11-05）。
- **`where` は書かなくても、未解決の role 制約が型に自動で付く**（確定, 2026-11-05）。`my twice(x) = x.add x` は `'a -> 'a where 'a: Add` と推論される。`x` の型が分からないまま現れた role の method は、その制約を残したまま進み、一般化のとき、環境由来でない型変数に付いた制約を型に持ち上げる。使う側で型変数が決まるたびに、その制約の解決が走る（`twice 1` なら `Add int`）。hover にも `where` が出る。
- **関連型は、新しい型変数と等式で表す**（確定, 2026-11-05）。`my first(c) = c.index 0` の型は、戻り値に型の射影（`'c::value` のような式）を書かず、新しい型変数 `'v` を置いて、制約の側に関連型の等式を持たせる。

  ```text
  first : 'c -> 'v where 'c: Index(int, value = 'v)
  ```

  `'c` が決まって `impl` が選ばれたとき、その `impl` の `type value = ...` が `'v` に代入される。型はいつも「変数＋制約」の形で、型の等価判定に関連型の簡約を持ち込まない。表記は旧版（`main:spec/2026-06-06-syntax-design.md`）の dump 表示 `Index(key, value = item)` に合わせる（暫定。通常引数を括弧に入れるか、`impl Index str int` のように並べるかは章7で決める）。
- **関連型の変数は普通の型変数で、等式は先に束縛しない**（確定, 2026-11-05）。`'v` には、`'c` が決まる前でも他の型との一致の制約が積まれる（上の `first xs` の結果を `str` として使えば `'v ≥ …` / `'v ≤ str` が積まれる）。`impl` が選ばれて `type value = ...` が分かったとき、等式 `'v = value` の制約が足されて、それまでに積まれた制約と合わなければ、その時点で型エラーになる。`'v` に関連型専用の規則はない。
- **一般化できない束縛に残った未解決の role 制約は、同じファイル（module）の終わりまで待つ**（確定, 2026-11-05）。`my z = default ()` のように値でない束縛は一般化されず、`'a: Default` は単相の変数のまま残る。同じファイルの使い方で決まればそれでよく、ファイルの終わりでも決まらなければ、その時点でエラーにする（どの型の `Default` か決まらない）。決まっていない型変数は、ファイルの境界を越えて公開されない。
  - **ファイルの終わりの検査には、そのファイルで見える `impl` の集合を使う**（確定, 2026-11-05）。そのファイルが読み込んだ（`use` で見える）`impl` と、そのファイルが自分で書いた `impl` が候補で、他のファイルにだけある `impl` は含めない（章6.2）。この集合を使うのは、**型が決まった role 制約**の検査（見える `impl` で一つに決まる／曖昧／見つからない）だけである。ファイルの終わりまで型変数が決まらなかった場合は、見える `impl` が一つしかなくても**その型に決めない**。role 制約が付いていてもエラー（どの型か決まらない）にして、注釈で決めさせる（確定, 2026-11-05。`impl` を足しても既存のコードが壊れないようにするため）。
- **`impl` の `where` は、head より構造的に小さくなければならない**（確定, 2026-11-05）。`impl` の `where` に書く各条件 `C t₁ … tₙ` は、次の二つを満たす。満たさない `impl` は宣言時に拒否される。解決の深さに上限は置かない。
  1. 条件の型の大きさの合計が、`impl` の head の型の大きさの合計より**真に小さい**（型構築子と型変数を一個ずつ数える）。
  2. どの型変数も、条件の中での出現回数が head の中での出現回数を超えない。

  **大きさの数え方（確定, 2026-11-07, ユーザーの決定）**: 大きさと出現回数は、**隠れた同名 field を取り除いた後の型**で数える（4.3: 隠れた field は型の上でも無かったことになる）。
  `impl R {x: int, x: int}` の 2 つ目の `x` は数えないので、`where {x: int}: R` は「真に小さい」にならず、宣言時に拒否される。隠れた field の無い普通の `impl` の扱いは変わらない。
  理由: 書いたままの大きさで数えると、隠れた field を好きなだけ足して「小さい」ことにでき、解決が停止しない registry が作れる（Lean: `CommonRoleFiniteShadowObstruction.finite_tree_registry_undecidable`）。

  **record の tail（`..'a`）を持つ head は、引き算を遅らせて解く**（確定, 2026-11-07, ユーザーの決定）。`impl R {x: int, ..'a} where 'a: R` のような head の `..'a` は、「head と要求同値になる任意の代入」ではなく、**record の引き算の結果として決まる残り**である。
  `R {x: int, ..'a}` の形の goal は、`'a` が未解決のうちは**解かずに保留する**（解いてはいけない）。具体的な record が来て、`{x: int, y: str} <: {x: int, ..'a}` のような判定で先頭の field が引かれたときに初めて、`'a` が `{y: str}` のように決まる（4.3: 受ける側の要求を残りに回すとき、先頭で書いた field の要求だけを取り除く）。
  そのため、`'a` を「head が隠れた同名 field を作るように」選び直すことはできず、`where` の各条件の意味は head と具体的な goal から一つに決まる。保留した goal は、具体化されるまで解決の対象にならないので、解決は止まらないことがある形にならない。
  理由: 任意の核の registry に対する Lean の反例（`CommonRoleFiniteTailObstruction.normalized_registry_undecidable`: `R {x:int, ..a} where R a` で `a := {x:int}` と捕まえると head が同値になる）は、この「任意の代入」の読みに依存していた。

  **variant の行で同じ tag を重ねて書いたときは、合流した後の形で数える**（確定, 2026-11-07, ユーザーの決定）。`impl R :{tick 'a, tick 'a}` のように同じ tag を重ねると、payload は合流して `union('a, 'a)` になり、型の意味は `:{tick 'a}` と同じである。大きさと出現回数は、`union(P, P) → P` のように縮約した後の形で数える。重ねて書くこと自体は、宣言のエラーにしない。
  合流は、型が分かるまで遅らせる（goal は型が確定した記述なので、照合の時点で合流済みの形になる）。別の tag を足すと要求が増えて型の意味が変わるので、見えない膨らみにはならない。見えない膨らみを作れるのは、同じ tag の重ね書きと、record の隠れた同名 field だけである。
  理由: 生の大きさで数えると、同じ tag を重ねて「小さい」ことにでき、解決が停止しない registry が作れる（Lean: `CommonRoleMergedObstruction.canonical_merged_registry_undecidable`）。
  **型変数の捕捉の後に初めて合流が起きる impl は、宣言時に拒否する**（確定, 2026-11-07, ユーザーの決定）。`where` が head より小さいことは、「型変数に何が入っても」成り立たなければならない。宣言の時点の大きさで小さく見えても、型変数が具体的な型に決まった後で、head の payload が合流して `where` が小さくなくなる `impl` は、宣言でエラーにする（利用時のエラーを増やさない）。
  例: `impl R 'a (:{tick (int, 'a), tick ('a, int)})` where `'a: R (:{tick ('a, 'a)})` は、`'a := int` の後で 2 つの payload が `(int, int)` に合流し、head と where が同じ大きさになる。この `impl` は宣言で拒否される。
  具体的な検査（有限で決められる十分条件）の形は、実装側で決める。
  **合流前の変数は、合流した後の payload をそのまま捕捉する**（確定, 2026-11-07, ユーザーの決定）。`impl R (:{tick 'a, tick 'b})` のように、同じ tag を別々の変数で重ねた head は、確定した goal `R :{tick int}` に対して、合流後の payload `int` を `'a` と `'b` の**両方**に捕捉する（`'a := int, 'b := int`）。合流前の値を型の同値から復元して分けたり（`'a := never, 'b := int` など）、任意に分割したりしない。
  そのため、この `impl` は goal の候補になり、`impl R (:{tick int})` も候補なら、二候補の曖昧性として報告される（6.2: 曖昧時の扱い）。
  **plain の型変数以外は、合流後の payload を分割しない**（確定, 2026-11-07, ユーザーの決定）。head の同じ tag を `box('a)` と `box('b)` のように別々の nominal の枝で重ねても、goal 側で合流して残った `box int` と `box bool` に別々に当てることはしない。この head は、そのような goal の候補にならない（`impl R (:{tick 'c})` のように plain 変数で受ける impl だけが当たる）。
  理由: 要求は union を含まない（4.7b）ので、合流後の payload を要求の枝に分割して当てると、要求に union を持ち込むことになる。
  **確定（2026-11-08, ユーザーの確認）: 「別々の nominal を分割して当てる」問いは起きない。** 共変の `box` は、`box int` と `box bool` を合流させると `box (int | bool)` の**一つの型**になる。head の `box('a) | box('b)` も `box('a | 'b)` になるので、plain 変数が合流後の payload を丸ごと捕捉する規則（上）を、共変な引数の中の変数にもそのまま当てる（`'a := int | bool`、`'b := int | bool`）。不変の `list` で別々の型を合流させると、`list (int | bool, int & bool)` の区間が `int | bool ≤ int & bool` を満たせず、**構築の時点で型エラー**になる。したがって、合流して残った 2 つの別々の nominal に分割して当てる場面は、共変でも不変でも起きない。上の「分割しない」の決定は、この理由で維持する（`box` が不変だから、という前の理由は取り下げ済み）。

  ```yulang
  impl Display (list 'a):
      where 'a: Display          // 良い: 'a は list 'a より小さい。list (list int) → list int → int と降りて止まる

  impl Foo 'a:
      where (list 'a): Foo       // 拒否: 条件のほうが大きい。Foo int → Foo (list int) → ... と終わらない
  ```

  この条件のもとで、role の解決は必ず停止する。
- **where の子の解決は、兄弟の更新が安定するまで遅らせる**（確定, 2026-11-08, ユーザーの決定）。ある `impl` の `where` の子が、その時点では候補が複数ある（曖昧に見える）ことがあっても、別の子が積む制約でその型が絞られれば、その子も後から決まる。兄弟と親は、更新のたびに作り直して再計算し、状態が変わらなくなったところで、初めて保留・曖昧・拒否を最終結果にする。途中の曖昧や保留は、言語のエラーではない。最終化は、6.3 の「ファイルの終わりまで待つ」と同じく、ファイルの終わりで安定した状態で行う。
  ここで型が絞られるのは、`impl` が一つしかないことからではない（`impl` が一つでも、その中の型変数は、それだけでは決まらない）。関連型の等式（上の「関連型は、新しい型変数と等式で表す」）を通して、別の子で決まった型が流れ込んだときなどに起きる。
  **兄弟の順序によらず結果は同じになる**（確定, 2026-11-08, ユーザーの回答）。`where Left 'a, Right 'a` は、`Left 'a` が成り立ち、かつ `Right 'a` が成り立つ、という連言であり、候補を選ぶ意味ではない。連言の項を入れ替えても、結果（保留・選択・曖昧・拒否、辞書の中身）は変わらない。
- **`impl` の `type name = ...` の右辺は、他の role の associated type を参照できない**（確定, 2026-11-05。**暫定: 次の項で一般化する方向に改訂**）。右辺に書けるのは具体的な型・型構築子・その `impl` の head に現れる型変数だけで、associated type は head の型引数から決まる一つの型になる。解決の途中で別の associated type を展開する必要は生じない。他の role の associated type を右辺で引ける構文は、必要が出てから足す。
- **`impl` の `type name = ...` の右辺で、他の role の associated type を参照できるようにする**（方向は確定, 2026-11-08, ユーザー: 「一般化できると思いますし、すべきです」）。参照は、上の「関連型は、新しい型変数と等式で表す」に従い、受け手が分かるまで遅らせて解く（新しい型変数と等式を積む）。**これは糖衣である**（確定, 2026-11-09, ユーザー）: 右辺の参照は、新しい型変数と、`where` の子（関連型の等式つき）に展開される。

  ```yulang
  impl Wrap (list 'a) where Container 'a:
      type out = list 'a::item
  // は次の表記の糖衣
  impl Wrap(list 'a, out = list 'b) where Container('a, item = 'b)
  ```

  関連型は名前つきの role 引数であり、名前なしの引数（`list 'a`）が決まれば、名前つきの引数の制約は一度に決まる。専用の仕組みは増えない。
  **関連型の等式で決まる変数は、出力にだけ使える**（確定, 2026-11-12, ユーザーの決定）。展開で現れる新しい変数（上の `'b`）は、その `impl` 自身の関連型の定義と、他の `where` の子の関連型の出力（名前つき引数）にだけ書ける。`where` の子の名前なしの引数（入力）には書けない。書いた `impl` は宣言時に拒否される。Paterson 的な「head より小さい」条件と「where 中の各変数の出現回数が head を超えない」条件は、`where` の子の**名前なしの引数だけ**で数え、この出力専用の変数は数えない。

  ```yulang
  // 受理: 'b は出力にだけ使う
  impl Wrap (list 'a) where Container('a, item = 'b):
      type out = list 'b
  // 拒否: 'b を別の子の入力に使う（Container の item が head より大きい型を返すと、解決が止まらない）
  impl Show (box 'a) where Container('a, item = 'b), Show 'b
  ```

  拒否する側を後から広げる余地（関連型の定義そのものに大きさの制限をかけて、入力にも使えるようにする案）は残す。出典: `notes/questions/2026-11-10-cycle70-associated-sugar-checking.md`。残る設計課題（上の展開に伴うもの）: (1) 停止性。右辺が作る goal を、`where` の子と同様に数え、Paterson 的な「head より小さい」条件の対象にする。(2) 関連型が head から決まる条件 `HeadDeterminesAssociated`（上）との関係。(3) 右辺の参照の循環。具体的な構文と条件は、設計して詰める（`notes/plan/m1-plan.md` の T13）。
- **自分の出力だけを根拠にした展開は保留する**（確定, 2026-11-12, ユーザーの決定「遅延」）。where の子の需要について、候補を調べるのに要る入力の頭を支える根拠が、その子を含む**まだ解けていない依存の輪**（祖先と自分の関連型の出力の等式）だけから来ているなら、その子の展開（候補の照合と子の生成）は保留にする。等式そのものは捨てず、通常の制約・同じ入力の需要のまとめ・再帰型（K2）の判定には使う。輪の外から根拠が来たら（ソースの制約や、解決済みの需要から）再開する。ファイルの終わりまで根拠が来なければ、最終の保留になる。宣言時の拒否は足さない。

  ```yulang
  impl R (list 'a) where R('a, out = 'b):
      type out = list 'b
  // 需要 R(list A, out = A): 親の出力の等式から A = list B（B は子 R(A, out = B) の出力）。
  // 子の入力 A の頭 list の根拠は、未解決の親子の出力だけなので、子は保留（無限に展開しない）。
  ```

  `Wrap(list int, …) → Container(int, …)` のように、子の入力の頭がソースから分かっている場合は、そのまま展開する。出典: `notes/design/2026-11-11-astra-general-boundary.md` の Item 4e の質問。

- **未解決の出力の輪だけを根拠にする需要は、輪の外にあっても保留する**（確定, 2026-11-13, ユーザーの決定「遅延」。上の「自分の出力だけを根拠にした展開は保留する」を下流へ広げる）。ある需要の、候補を調べるのに要る入力の頭の根拠が、まだ解けていない依存の輪（関連型の出力の等式）からしか来ていないなら、その需要が輪の一員でなくても、展開を保留にする。等式は通常の制約・同じ入力の需要のまとめ・再帰型（K2）の判定には使う。輪と無関係な根拠（ソースの制約、解決済みの需要）が来たら再開する。宣言時の拒否は足さない。

  ```yulang
  impl Container (list 'a):
      type item = 'a
  impl Wrap (list 'a) where Container('a, item = 'b):
      type out = list 'b
  impl P (list 'a):
      where Container('a, item = 'z), Wrap('a, out = 'z), P('a)
  // P(list (list X)) で X が未知: 次の段の P と Wrap の入力の頭は、未解決の Wrap/Container の出力からしか分からないので保留。
  ```

  出典: `notes/design/2026-11-13-termination-proof-plan.md` の 4〜5 節。

- **片付いていない impl の出力を根拠にした展開は保留する**（確定, 2026-11-13, ユーザーの決定「遅延」。上の二つの「輪だけを根拠にしたら保留」を、輪にならない場合へ広げる）。impl を選んだ需要のうち、自分の where の子にまだ保留のものが残っているもの（片付いていない需要）の関連型の出力は、ほかの需要が**候補を調べるのに要る入力の頭**の根拠に使えない。そうした根拠しかない需要の展開（候補の照合と子の生成）は保留にする。ソースの制約や、片付いた需要（子まで全部解けたもの）の出力が根拠になれば再開する。等式そのものは捨てず、通常の制約・同じ入力の需要のまとめ・再帰型（K2）の判定には使う。ファイルの終わりまで根拠が来なければ、最終の保留になり、汎化した型の制約として残る。宣言時の拒否は足さない。

  ```yulang
  impl W (list 'x) 'y 'm:
      where 'y: C('m, item = 'u)       // C は 'm が分かるまで保留なので、W は片付いていない
      type out = list (list 'u)        // out の形は見えているが、展開の根拠には使わない
  impl P (list (list (list 'a))) 'b 'm:
      where (list 'a): W('b, 'm, out = 'z, …)
      where (list 'a): P(list 'b, 'm)
  // 再帰の P の入力の頭は、片付いていない W の出力からしか分からないので保留。
  // 使わせると、P の子の入力が一段ずつ長くなり、需要が無限に増える（依存は輪にならない）。
  ```

  出典: `notes/design/2026-11-13-termination-fresh-analysis.md`（例の全体と、輪だけの保留では止まらないことの議論）。

- **同じ入力の需要はまとめる**（確定, 2026-11-12, ユーザーの決定。Yulang2 の「全ての通常引数に共通の型変数があれば併合する」規則（`main:spec/2026-06-02-role-system.md`「簡約について」2）を洗練したもの）。同じ role の需要が二つあり、**すべての名前なしの引数が同じものを指す**（同じソースの識別子であるか、等式で同じと示せる）とき、二つの関連型の出力を等しいとし、需要を一つにまとめる。impl を選ぶ前、保留のままでも行う。根拠は下の「関連型は head から決まる」で、解決できる需要についてモデルを失わない。Yulang2 の条件（共通の型変数がどこかの端点にある）は使わない。中心を持たない区間の上では、実際の引数が同じことを保証しないため。

  ```yulang
  my sq2 a b = a * b + a * b
  // Mul(a, b, out = 'o1) と Mul(a, b, out = 'o2) は、名前なしの引数がどちらも a, b なので一つにまとまり、'o1 = 'o2
  ```

  - **名前なしの引数は入力、名前つきの引数は出力**（確定, 2026-11-14, ユーザー:「名前無し区間は引数で，名前あり区間は出力」）。まとめるかどうかは名前なしの引数だけで決まり、名前つきの引数（関連型の出力）の有無や違いは関係しない。片方にしか出力の指定がない需要もまとめ、まとめた需要はすべての出力の指定を持つ。候補の照合も名前なしの引数（head）だけで行い、出力の指定で候補を絞ったり曖昧さを解いたりしない（6.2）。選んだ `impl` の関連型がまとめた需要の出力の指定と合わなければ、その時点で型エラーになる（上の「関連型は、新しい型変数と等式で表す」）。

    ```yulang
    impl Start (list 'a):
        where 'a: R(out = int)
        where 'a: R
    impl R int:
        where Z
        type out = list int
    // (list int): Start で 'a = int。'a: R と 'a: R(out = int) は一つにまとまり R(int, out = int) になる。
    // R int を head で選ぶと out = list int が out = int と合わず、型エラー。
    ```

- **`impl` の関連型の右辺は、head から決まらなければならない**（確定, 2026-11-07。ユーザーの決定）。head の**隠れた同名 field**（`{x: int, x: 'a}` の 2 つ目の `x`。型の上では無かったことになる。章4.3）を除いた head から、右辺が使う型変数が決まらない `impl` は、宣言時に拒否される。
  例: `impl R ({x: int, x: 'a}): type value = 'a`。goal `R {x: int}` に対して `'a` は任意の型で成り立つので、関連型 `value` が `int` にも `bool` にもなり、同じ `impl` のため「候補の impl が複数ある」曖昧さの検査にも当たらない。
  必要な条件は `HeadDeterminesAssociated`（任意の `impl` と、head が要求同値になる任意の二つの代入について、関連型の右辺も要求同値になる）。具体的な検査の形（隠れた field を先に除く、など）と、その十分性は未証明。
  出典: Lean の反例 `CommonRoleAssociatedExactness.checked_registry_counterexample`（B4 の E2）。

- `role` の body の `where` は、その role の method に継承される。`impl` の body の `where` は、その `impl` が候補になるための前提になる。

## 6.4 `x.method` の解決　〔確定〕

`x.method` は、すぐには解決されない。**`x` の型の下界が分かって、その型に `.method` があるとき**に初めて解決される。

```yulang
x.add y
```

- 候補の探し方は、まず receiver の型に結びついた field と、`with:` で定義した method。次に role の method と effect 行の method。
  **この順序は仕様**で、同じ名前が複数の段にあるときは**この順で先に見つかったものが選ばれる**（確定, 2026-11-04）。
- **`x` が `ref 'e 'a` のとき、探すのは `ref` だけである**（確定, 2026-11-05）。中身の `'a` には降りない。中身の method を使いたいときは、値を読み出して `$n.add 1` と書く。`ref` は普通の nominal な型として扱い、特別な委譲規則はない。
  `ref` に対する method は、型の一部だけを決めた形に対しても定義できる。例えば `ref _ int`（effect 行は任意、中身は `int`）に特化した method を `with:` や `impl` で書ける。

```yulang
my $n = 0
&n.get                 // ref の method
$n.add 1               // 中身の int の method
&n.add 1               // エラー: ref に add は無い（ref _ int に特化した add を定義すれば別）
```

- **receiver の型が union のとき**（確定, 2026-11-05）。union のメンバーのうち、その method を**持つ型が一つだけ**なら、その型の method に決まる。決まったら、receiver はその method の receiver 型への**普通の cast 境界**として扱われる（章6.5）。他のメンバーはその型へ cast され、規則がなければ「暗黙の cast が見つからない」エラーになる。method を持つメンバーが**二つ以上**あれば曖昧エラーで、利用者に型の注釈を入れさせる（メンバーの並び順では選ばない）。

  ```yulang
  my x = if c: 1 else: user_id_value     // int | user_id
  x.add 2                                 // Add を持つのは int だけ → int の add に決まり、user_id 側は int へ cast
  x.show                                  // int にも user_id にも show がある → 曖昧エラー
  (x: int).show                           // 注釈で期待型を与える。user_id 側が int へ cast される
  ```

- method が解決されるまで、それを含む SCC は解かれない。
- SCC がこれ以上変化しなくなったとき、解決していない method は、role の method か record の field として解釈される（確定, 2026-11-04）。
  - **receiver の型が最後まで分からないとき、role の method を先にする**（確定, 2026-11-05）。その名前の method を持つ role がスコープにあれば role の制約として扱い（`x.add x` は `'a: Add`、章6.3）、なければ record の field として扱う（`p.x` は `p: {x: 'b}`）。スコープに同名の method を持つ role が**複数**あれば曖昧エラーで、型の注釈を入れさせる。型が分かっているときの順（field が先）とは逆になる。分かっている型に field があるなら、それが具体的な手がかりになるが、未知の receiver は field を持つかどうかも分からないため。
  - **解釈は SCC の解決時点で固定される**（確定, 2026-11-05）。その SCC の中で receiver の型が分かれば、分かった型に対する順（field が先）で解く。SCC が変化しなくなっても分からなければ、その時点で role（または field）として解釈され、一般化された型にその制約が残る。呼び出し側で後から型引数が決まっても、定義の解釈は書き換わらない。`f(x) = x.size` が `where 'a: Size` と推論されたなら、呼び出しで `'a := box` と決まって `box` に field `size` があっても、`Size box` の `impl` が無ければエラーである（field に切り替わらない）。

出典: `main:spec/2026-06-04-method-selection.md`、`main:web/docs/ja/reference/modules.md` §Dot selection

## 6.5 `cast`　〔境界と合流は確定、他は仮採用〕

```yulang
struct user_id { raw: int }

cast(x: user_id): int = x.raw
cast(x: int): user_id = user_id { raw: x }
```

- `cast(x: A): B = body` は、`A` から `B` への**暗黙の変換規則**を登録する。
- `cast` は他の module の型どうしにも書ける（確定, 2026-11-04）。有効になるのは、その `cast` が `use` で見える範囲だけ（D6 の method と同じ規則）。同じ `A → B` が複数見えたら曖昧エラー。
- 推論された値の型と、既知の期待型がぶつかる境界で、登録された規則が適用される。

```yulang
my id: user_id = 1          // int → user_id
my back: int = id           // user_id → int
my use_int(n: int) = n + 1
use_int id                  // 引数の境界で int に変換される
```

- cast が入るのは、**期待型が分かっている境界**: binding や引数の注釈、関数の引数。
- **分岐の合流**（`if` / `case` の arm、effect arm の結果）で型が違うときは、cast を入れず**union として一度持つ**（確定, 2026-11-04）。
  その後で期待型が現れたら、その型へ cast される。何も期待されていなければ、**曖昧さを警告する**（エラーではない）。

```yulang
my x = if c: 1 else: user_id_value     // int | user_id の union。どちらの型になるかはここでは決まらない
my n: int = x                           // 期待型 int が来たので、user_id の側が int に cast される
my y = x                                // 何も期待されていない → 曖昧さの警告
```

- union の値に期待型が来たとき、各メンバーを別々に扱う。期待型と同じメンバーはそのまま通り、違うメンバーはその型への cast を探す。**一つでも cast が見つからないメンバーがあれば、型エラーにする**（暗黙の cast が見つからない。実行時に失敗させる扱いはしない。確定, 2026-11-05）。

```yulang
my y = if c: 1 else: "text"            // int | str
use_int y                               // エラー: str から int への暗黙の cast が見つからない
```

- 変換の定義を変にするほうが悪い、という立場。合流は許し、どちらに寄るかは期待型に任せる。
- **期待型のない裸の式では変換されない。** `id` だけなら `user_id` のまま。
- 該当する規則がなければ「暗黙の cast が見つからない」エラー。一致する規則が複数あれば ambiguous で拒否される（Yulang は勝手に選ばない）。
- cast は遅延しない。境界に着いた時点で body が走る。重い変換は普通の関数にして、呼び出しを明示する。
- **型引数を持つ型にも cast を書ける。ただし target は source より大きくならない**（確定, 2026-11-05）。`cast(x: A): B` の `A` と `B` に型変数が現れるとき、次の二つを満たさなければ宣言時に拒否する（章6.3の `impl` の条件と同じ形）。
  1. `B` の型の大きさ（型構築子と型変数を一個ずつ数える）が、`A` の大きさ以下である。
  2. どの型変数も、`B` での出現回数が `A` での出現回数を超えない。

  どんな型を入れて具体化しても、型変数を含む cast の行き先は元より大きくならない。大きさが変わらない cast には循環もあり得る。有限な宣言集合と出発型を固定すると、明示規則の連鎖で到達する型は、そこに現れる有限の型構築子集合とサイズ上界の中にある。固定した ground cast が型を大きくする場合も、宣言された target のサイズを上界に含めればよい。同じ型を繰り返し展開しない有限集合上の探索は、深さ制限なしで停止する。

  ```yulang
  struct box 'a { value: 'a }

  cast(x: box 'a): 'a = x.value             // OK: 'a は box 'a より小さい
  cast(x: 'a): box 'a = box { value: x }    // エラー: 行き先が元より大きい。box (box (box ...)) と増え続ける
  cast(x: pair2 'a 'b): pair 'a 'a = ...    // エラー: 'a の出現が source より多い
  ```

  - 型引数を固定した cast（`cast(x: box int): int`）は、これまでどおり書ける。
  - 型変数が source に現れない target は、条件 2 により宣言時に拒否される（行き先が決まらない）。

- **`cast` の本体は純粋でなければならない**（確定, 2026-11-05）。本体が effect を起こす cast は、宣言時にエラーにする。暗黙に入る変換に、effect が行へ隠れて増えることはない。失敗しうる変換や、入出力を伴う変換は、普通の関数にして呼び出しを明示する。関数に cast を通した wrapper も、呼び出しの effect 行を増やさない。
- **cast は関数の型の内側にも通る**（確定, 2026-11-05）。期待される関数型 `A' -> B'` に、値の関数型 `A -> B` が cast で合うとき（`A'` から `A` へ、`B` から `B'` へそれぞれ cast できるとき）、関数は包み直される。引数側は反変、戻り値側は共変に cast が入る。包み直しは境界に着いた時点で作られ、中の cast は呼び出しのたびに走る。

```yulang
my apply_to_id(f: user_id -> int) = f id_value
my inc(n: int) = n + 1
apply_to_id inc            // OK: inc : int -> int は、引数側に user_id → int の cast が入った関数として渡る
```

- **cast は、方向を持つ位置に沿って通る**（確定, 2026-11-05）。関数の引数（反変）・戻り値（共変）に加えて、tuple の成分・record のフィールド・variant の payload（いずれも共変）にも通る。通るときは成分ごとに cast して、新しい値を作る。変換の量は型の大きさで決まり、データの大きさには依らない。

```yulang
my p = (id_value, "a")            // (user_id, str)
my q: (int, str) = p              // 成分ごとに cast: (int, str)
```

- **nominal な型の型引数のうち、無限に入れ子になりうるもの（`list 'a` など）は不変で、cast も通らない**（確定, 2026-11-05。範囲は 2026-11-08 に訂正: ユーザーが「`box` は共変。不変になるのは無限に入れ子になっているとき」と訂正した。理由は型変換のコスト: 再帰的な構造の中身を cast で変換すると全体を作り直すことになるので、cast を通さず不変にする）。不変な引数は `(lower, upper)` の区間として持ち、実際の引数は一つの型に決まる。すでに型が決まった `list user_id` は `list int` の場所には渡せない。有限の入れ子の `box 'a` は共変で、`box user_id` は `box int` の場所に渡せる（変換が一段で済む）。
- **不変な引数は、中心を持たない区間 `(lower, upper)` で持つ**（確定, 2026-11-08, ユーザーの説明。出典は旧世代の `main:spec/2026-06-02-role-system.md`「不変区間規則」。role の解決の土台はこの区間で、型の同値で点として扱わない）。
  - **実際の引数の名前（中心）は明示して持つ**（確定, 2026-11-14, ユーザーの決定「2 でいいのでは。……実際においてしまったほうが早い」）。区間の内側にある実際の引数を指す識別子（中心）を、区間と一緒に持つ。中心は `lower ≤ 中心 ≤ upper` を満たす未知の型の名前で、具体的な型を選ぶものではない。role の解決（候補の照合、曖昧、K2）は今までどおり区間の端点と既知の頭で行う。中心は「同じ型変数を使い回すと同じ実際の引数を指す」（上の「同じ入力の需要はまとめる」と、impl の型変数の共有）を表すためだけに使う。実装が共有の情報を失ったことを理由に需要を保留にする規則は足さない（「中心が常に存在する」ことを証明する代わりに、表現に置く）。
    ```yulang
    impl W (:{tick 'a}) 'b:
        type anchor = 'a
        type out = :{tick 'b}
    impl P (:{tick :{tick 'a}}) 'b:
        where (:{tick 'a}): W('b, anchor = 'z, out = 'z)
        where (:{tick 'a}): P('b)
    my trigger(x: 'a, b: :{tick 't}) = (:tick (:tick x)).pump b
    // b の中心は二つの子で共有される。W から A = :tick b、次の段で b = :tick b となり、K2 で拒否される。
    ```
    出典: `notes/design/2026-11-14-actual-boundary-agreement.md` の §4 の質問。
  - 型変数は、下界と上界の組を持つ。表示では `bool | int | 'a & float & complex` のように、真ん中に型変数を置いて書く。内部では `(bool | int | 'a, 'a & float & complex)` で、`lower = bool | int | 'a`、`upper = 'a & float & complex`。lower と upper の両方に出る変数は、表示のときだけ重複を隠す。
  - **同じ実引数を 2 つの区間で満たすときは、両区間の下界を lower 側へ、上界を upper 側へ足す。** `'a <: box 'b` と `'a <: box 'c` があれば、`'a <: box ('b | 'c, 'c & 'b)` として扱う。共起分析（lower と upper の両方に現れる変数の併合）にかけると、たいていは `'b = 'c` が結論されて、不変になる。
  - 区間は、実際の引数が `lower ≤ 実型 ≤ upper` を満たすことを要求する。そのため `lower <: upper` を制約として戻す。両側が同じ単一の具体型 `T` の区間は、`T` に畳む。
  - **区間の端点の型が不変な引数を持つときは、その内側でも同じ規則を再帰的に適用する**（確定, 2026-11-08, ユーザーの確認）。併合で生まれる交差条件 `loA <: upB`、`loB <: upA` と `lower <: upper` は、特別な規則ではなく通常の部分型制約として解く。端点が `list (list int)` と `list (list float)` のとき、外側の区間の交差条件 `list (list int) <: list (list float)` を解く途中で、内側の `list` の区間がまた併合される。入れ子の深さに上限はなく、各層は同じ規則に従う。
  - **不変な引数の中にある共変・反変の位置は、不変として扱ってよい**（確定, 2026-11-08, ユーザーの説明。「不変のなかの共変は不変として捉えてよい」、反変も同じ）。たとえば `list` の不変な引数の内側にある `box` の共変な引数は、そこでは共変として cast せず、不変な区間として持つ。外側が不変なら、内側の宣言上の向きは区間の扱いを変えない。例: `list (int | 'a & float -> int)` は、不変な `list` の引数が、区間 `int | 'a & float` を引数に持ち `int` を返す関数になっている形である。この関数の戻り値のような共変の位置も、引数のような反変の位置も、`list` の内側では共変・反変として扱わず、不変な区間として持つ。
  - **不変な引数は、区間か、区間の両端が同じ constructor で確定した形のどちらかになる**（確定, 2026-11-08, ユーザーの説明。型の単純化）。不変な引数の区間は、上界と下界がどちらも同じ constructor（共変の `box` でもよい）になると、その constructor が確定し、中身はまた不変な区間になる。例: `list` の引数の区間が `(box A, box B)` なら、`list (box (A, B))` と単純化する。`list (box (int | 'a & float))` もありうる。両端の頭が違う場合（下界 `box A`、上界 `list B` など）は、区間のまま残る（確定, 2026-11-08, ユーザーの確認）。したがって不変は入れ子になる。上の「共変・反変の位置も不変として扱う」は、この単純化の帰結である。
  - **型変数の極性は、型宣言のときに決める**（確定, 2026-11-08、同日訂正済み。ユーザーの説明。推論時には要らない）。型変数が**無限に入れ子**になっていれば不変（型区間）、そうでなければ通常の見方（位置による共変・反変。`box 'a` は共変）。理由は型変換（cast）のコスト。
    - **「無限に入れ子」の判定規則（確定, 2026-11-08, ユーザーの決定。Pro の候補 1）**: 型宣言群から、引数ごとに次で向きを決める。
      1. その引数が payload（field、variant の payload、tuple の成分など）に実際に使われなければ `unused`（名前が自己参照の実引数に書かれているだけの phantom を含む）。
      2. 使われる引数について、cast が値を**今その場で辿る**辺（field・variant payload・tuple など）を依存グラフに入れる。**関数を包む位置で、即時に辿る道を切る**（関数の内部の使用や極性は消さない。wrapper の作成時と、呼び出しごとの変換の費用を分ける）。
      3. 使われる payload へ届く道の上に、任意回数反復できる nominal 展開の cycle があれば、その引数は**不変**。cycle が無ければ、通常の極性（関数の引数は反転、結果と通常の data 成分は保持、callee の既知の向きと合成）で、正だけなら共変、負だけなら反変、両方なら不変。
      例: `box 'a`・`box2 'a`・`reset 'a`（再帰枝が `int` に固定）・`stream 'a`（再帰が関数に包まれている）は**共変**。`chain 'a`・`left 'a`/`right 'a`（別名を通る cycle）は**不変**。`phantom 'a` は `unused`。
      理由: 型変換のコスト。`stream` は、遅延された再帰を、呼び出しのたびに 1 要素ずつ変換できるので、共変としてよい（ユーザー: 「stream が共変になるのは悪くない。型変換も簡単」）。
      有限の判定は、宣言群の `(宣言 ID, 引数番号)` を頂点にした到達可能性と SCC の不動点で行う。外部の opaque な型は、その module が公開する検証済みの引数 metadata を参照する。
  - **要確認（上の規則から Claude が導いた帰結。ユーザーの言葉ではない）**: 合流の結果は、引数の向きで変わる。共変の `box` なら、`box int` と `box bool` の合流は `box (int | bool)` になり、エラーにならない。不変の `list` なら、`list int` と `list bool` の合流は `list (int | bool, int & bool)` の区間になり、`int | bool ≤ int & bool` を満たせず型エラーになる。
- **配列（list）の literal の要素型は `int | '_a` のように、後で決まる部分を持つ**（確定, 2026-11-05）。`'_a` は値制限で一般化されない弱多相の変数で、後の使い方で決まる。`my e = []` の `'a` が後で決まるのと同じ仕組み。`'_a` が決まったとき、literal の要素は**構築位置に遡って**、その型への境界として cast される。literal の各要素は、`'_a` が決まるまで保留された境界を持つ。

```yulang
my xs = [1]                    // list (int | '_a)。'_a は弱多相
my ys: list user_id = xs       // '_a := user_id。要素 1 に int → user_id の cast が入り、xs は list user_id として作られる
```

  - 同じファイルの終わりまでに `'_a` が決まらなければ、cast なしで要素の型の合流（上の例では `int`）に決まる（章6.3の、ファイルの終わりまで待つ規則と同じ）。
  - 値を作る場所以外（すでに型が決まった `list user_id` の値）では、中身は cast されない。
- **保留された境界は、不変な型引数にだけ付く**（確定, 2026-11-08, ユーザーの決定。2026-11-05 の「list に限らない」を、共変の訂正に合わせて範囲を明確にした）。不変の型引数を持つ nominal 型の構築（`list` の literal のほか、`struct` の literal や `enum` の constructor で不変な引数を持つもの）は、型引数に当たる値に、すべて同じ保留された境界を持つ。`'_a := int` と決まれば、値は構築位置で `int` に cast される。list literal はこの特別な場合である。**共変の引数には保留を付けない**: `box { value: id_value }` はそのまま `box user_id` になり、`box int` の場所へは、後から共変で cast される（変換が一段で済むため）。理由は、不変にする理由（構築済みの再帰データの中身を cast すると全体を作り直す費用がかかる）と、保留する理由が一致するから。

### `from` 付き variant

```yulang
enum app_err:
    path from path_err
    parse from parse_err
```

- variant に `from` を付けると、variant そのもの（`app_err::path` が `path_err` を包む）と、`path_err` から `app_err` への変換規則が作られる。
- payload は 1 つ、source と target はどちらも nominal でなければならない。
- `error` 宣言の `from` は、`wrap` と `up` も広げて、狭いエラーを同時に捕まえるようにする。

出典: `main:web/docs/ja/reference/casts.md`

### 注意: `cast` 宣言と `Cast` role は別物

標準ライブラリには `.cast` method を持つ `std::core::convert::Cast` という role があるが、`cast` 宣言はこの role を**実装しない**し、呼びもしない（罠 T6）。
同じ名前は意図的で、変える予定はない（確定, 2026-11-04）。

## 確認してほしい点

- **K1** receiver の無い member（6.1）の整合条件。**解決（2026-11-08, ユーザーの決定）: 宣言では何も拒否しない。**
  member の型が関数型で、少なくとも 1 つ引数を取ることは、6.1 のとおり。それ以上の整合条件（role の型引数が戻り値や引数に出ること）は、宣言の時点では検査しない。
  理由: role の型引数を決める手がかりは、呼び出しの引数と戻り値の型であり、それは型が分かった後で決まる。未解決の role 制約は、`where` を書かなくても型に自動で付き（6.3）、一般化できない束縛に残ったものは、同じファイルの終わりまで待つ（6.3）。終わりの検査でも決まらなければ、そこで初めてエラーにする。
  たとえば、role の型引数が戻り値にも引数にも出ない member（`our size: str -> int`）を呼ぶと、`'r` を決める手がかりがなく、その制約は最後まで未解決のままなので、ファイルの終わりの検査で「解決できない」と報告される。引数にだけ出る member（`our render: 'r -> str`）は、引数の型が分かった時点で解ける。宣言のための特別な規則は要らない。

- **K2** 再帰型（正則）を含めたときの、role の解決の停止（6.3）。6.3 は「`impl` の `where` が head より構造的に小さければ、解決は必ず停止する」と述べるが、
  これは有限の木を前提にした議論に見える。Lean の記録（`notes/handoff/2026-11-07-common-demand-and-foundations-results.md` §6、`CommonRoleRegularObstructions`）では、
  既存の宣言 checker が受理する規則 `R(F(G(G a), b)) requires R(F(a, G b))` と、再帰型 `A ≈ G A` から、要求同値でも再訪しない goal の無限列が作れ（`chain_fresh`）、
  自然数の減少による停止の議論は不可能（`no_natural_descent_measure`）と証明された。
  ただし、Yulang のソースからこの goal が実際に生成できるかは未確認で、B4 自体が偽とも決定不能とも示されていない。決める話ではなく、未決として書き残す。
  **2026-11-07 の更新**: B4 の Lean 検証（`CommonRoleRegularResolutionObstruction.amended_registry_undecidable`）で、宣言 checker を通る registry から、再帰型の goal の解決可否が停止問題と同じ難しさになることが証明された。
  つまり「構造的に小さい」という宣言時の規則だけでは、再帰型を含む goal の停止は保証できない。
  ユーザーの決定（2026-11-07）: role 単位の非巡回の検査（`Display (list 'a)` が `Display 'a` を要求する宣言まで弾く案）は**採らない**。引数が小さくなる再帰は許す。
  残る未決（Yulang のコードに現れる）: 再帰型を role の型引数に渡す goal を、どう扱うか。選択肢は、(a) 再帰型を含む goal の解決を拒否または曖昧として報告する、(b) 再帰型でも停止を保証する追加の宣言検査を設ける（その十分性は未証明）。ユーザーに 1 問ずつ聞く。
  **決定（2026-11-07, ユーザー, 確定）: 構造的な再帰型（自分自身を指す無名の型）が role の型引数に現れる goal は、解決に入る前に拒否する。**
  「再帰型のため role を解決できない」と報告する。解決の深さに上限は置かない（6.3 の「解決の深さに上限は置かない」は変えない）。辞書は常に有限で、coinductive は採らない。
  これで、Lean の反例（同じ goal に戻らず新しい goal が無限に続く形）も、同じ goal に戻る形も、解決に入る前に除かれる。解決に入る goal は有限の木だけになるので、6.3 の「where が head より構造的に小さければ停止する」の議論がそのまま成り立つ。
  **決定（2026-11-07, ユーザー）: 拒否の位置。** 再帰型が型引数の深い位置（例: `list` の中）にあるだけなら、呼び出しは拒否しない。解決が**その再帰型を head とする goal に到達したとき**に拒否する。
  例: `impl Len (list 'a)`（where なし）に対する `len [loop 1]` は通り、`impl Show (list 'a) where Show 'a` に対する `show [loop 1]` は `Show μ`（μ は再帰型）に降りたところで拒否される。報告では、どの impl の where で到達したかを示す。
  **決定（2026-11-07, ユーザー）: 名前の付いた再帰型は対象外。** `enum tree` のように名前で終わる再帰型は、通常どおり解決する（`impl Show tree` に名前で当たる）。拒否されるのは、名前の無い構造的な再帰型だけ。
  **決定（2026-11-07, ユーザー）: 拒否の場所を一つ足す。** impl の head を goal に照合するとき、head の非変数 pattern が名前の無い構造的な再帰型の constructor を調べる必要が出た時点でも、「再帰型のため解決できない」と拒否する。
  例: `impl Check {box: {tick: 'a}} where Check {box: 'a}` に、`μ = {tick: μ}` を使う `Check {box: μ}` を解決させると、`{tick: 'a}` を μ の中身に当てる時点で拒否される（goal の根 `{box: …}` は再帰型ではないので、根の規則だけでは拒否できなかった）。
  `'a` のように再帰型を変数で捕まえるだけの照合（`Len (list μ)`）は通る。理由: 根の規則だけでは、再帰型を `pair` などの中に残したまま、互いに同値でない goal を無限に作る registry が作れ、解決の停止が停止問題と同じ難しさになる（Lean: `CommonRoleReachedRootObstruction.reached_root_registry_undecidable`）。
  **拒否と曖昧性の優先順位（確定, 2026-11-08, ユーザーの決定）: 拒否が先。** goal に当たる impl の候補のうち、どれか一つでも「名前の無い構造的な再帰型の constructor を調べる」必要があるなら、他の安全な候補がいくつあっても、「再帰型のため解決できない」と拒否する。安全な候補が 2 つ以上あっても、1 つだけでも、曖昧性や選択より先に拒否する。impl の宣言の順に依存せず、調べる候補を避けて選ぶこともしない。
  例: `impl Check ({box: 'a})`（変数で受ける）と `impl Check ({box: {next: 'b}})`（中身を見る）が同時に見えるとき、`check {box: loop 0}`（`loop 0` の型は再帰型 μ = {next: μ}）は、前者が当たるだけでは通らず、後者のために拒否される。
  **決定（2026-11-12, ユーザー）: 循環の上にある根も K2。** 再帰型の判定は、型のグラフで「根（または head の非変数 pattern が調べる位置）が**循環の上にある**か」で行う。循環は名前つきの型（`list` など）の**引数**を通ってもよい。名前つきの型の中身（body）は開かない（名前で終わる再帰型は今までどおり対象外）。
  例: `my nest(n) = [nest n]` の結果の型は μ ≈ list μ で、根そのものが循環の上にある。`display (nest 0)` も `len (nest 0)` も「再帰型のため解決できない」と拒否する（`impl Len (list 'a)` に where がなくても）。一方 `len [loop 1]` の型 `list ν` は、根の `list` から ν の循環に入るだけで、根は循環の上にないので通る（上の決定のまま）。
  理由: 根の頭が名前つきの型だと、「無名の構造的な型」だけを見る規則では `Display μ` → `Display μ` と同じ需要に戻り続け、解決が止まらない（Lean: `GeneralNominalProgressObstruction`）。
  K2 は、これで **確定**。B4 の修正 statement は「goal の型・行から構造的な再帰型を除いた有限木」を前提に書き直す（`notes/questions/2026-11-07-b4-regular-resolution-decidability.md`）。
