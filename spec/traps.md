# 罠台帳

直感と違う挙動、仕様と表示・実装の乖離を書き留める。ユーザーが随時足す。
各項目は「何が起きるか → どちらが正か → 状態」を書く。正しさの判断はユーザーが行う。

## 書式

```
### <短い名前>
- 状態: 確定 / 要確認 / 未定
- 現象: <最小の .yu 例と、実際に起きること>
- 期待: <言語として約束したいこと>
- 乖離の原因: <分かっていれば>
- 関連: <章 / 出典>
```

## 項目

### T1. effect 行の区切りは `,`（`;` は廃止）
- 状態: 確定（ユーザー説明, 2026-11-04）
- 現象: 旧表記と新表記は次のとおり。

  ```text
  旧: 'a [undet; 'b] -> ['b] list 'a
  新: 'a [undet, 'b] -> ['b] list 'a
  ```

  行の中の effect と行変数（`'b`）の区切りは `,` だけを使う。`;` は廃止された。
- 期待: 仕様・例・表示のすべてで `,` を使う。
- 注意: main の既存文書（`web/docs`、`spec/`、`notes/` など）には旧表記 `;`（例: `[var<α>;]`）が残っている。素材から起こすときは新表記に直す。
- 閉じた行と開いた行の区別（確定, ユーザー回答 2026-11-04）: 記法としての区別は、**行変数が生で（明示的に）書かれているかどうか**だけ。
  `[undet]` のように変数を書かなければ閉じた形式、`[undet, 'b]` のように変数が出現すれば開いた形式の表記になる。
  `;` による区別はもう無い。
  - 注釈と表示では同じ意味で扱ってよい（確定）。注釈は閉じて書いても開いた注釈になり、表示ではしばしば開く（T3）。
- 関連: 章1 字句、章5 effect と handler、章7 型の表示

### T2. 反変位置の effect 注釈は「引いてよい」という属性を型変数に与える
- 状態: 確定（ユーザー回答 2026-11-04）
- 現象: 引数の型注釈の中の `[undet]` は反変位置にある。

  ```yulang
  my f(g: 'a -> [undet] 'b) = ...
  ```

  `[undet]` は「`g` はちょうど `undet` を起こす」という固定ではなく、
  「**`undet` を引いてもよい `'c`**」と解釈される。許可であって義務ではない。**引かなくてもよい。**
- 仕組み: 注釈は、行の**型変数そのもの**に「これらの effect を引ける」という属性を足す。
  注釈に書かれていない effect は、handler を書いても引けない。

  ```yulang
  // f(a: [io] _) と注釈していなければ、次の handler は io を引けない
  catch a:
      io::write x, k -> ...
  ```

- 推論結果の例:

  ```text
  ('a -> [undet, 'd] 'b) -> 'a -> ['d] list 'b
  ```

  引数側の行は `[undet, 'd]`、結果側の行は `undet` を引いた残り `['d]` になる。
  注釈に書いた `[undet]` が、結果の型に「そのまま」残るわけではない。
- 複数書いた場合: `[undet, io]` は「`undet` か `io` を引いてよい `'c`」。両方を引く必要はない。
- `[_]` は glob で、全 effect を列挙したのと同じ意味（`[io, undet, console, ...]`）。全部引いてよい（章5.5）。
- `undet` 以外の effect を渡してもよい。`var 'b` を持つ関数を渡すと `'c = var 'b` になる。
  ただし `f` の中で `var 'b` を引こうとしても**引けず**、handler に捕まらず素通りして、
  型変数 `'c` として結果の型に現れる。
- 要確認: 上の `catch` の例の正確な構文と、引けないときに handler の他の分岐がどうなるか。実行して確かめる。
- 関連: 章5 effect と handler、`main:spec/2026-05-31-effect-variable-subtractable.md`、`main:notes/design/handler-row-subtraction.md`

### T3. 共変位置の effect 注釈は「今は具体的な型が見えない」を許す
- 状態: 確定（ユーザー回答 2026-11-04）。例は要確認
- 前提: 型注釈は**その場で局所的に使い、許す型**であって、effect は基本的に注釈を素通りして勝手に推論される。
  注釈の effect 行は閉じた形式で書くが、実際には開いた注釈として扱われる。表示でもしばしば開く。
  effect がどこで注入されるかは分からないので、`list 'a -> [undet] 'a` のような関数はどこにでもある。
- 現象: 共変位置（戻り値側など）の `[io]` は、行変数に「**今は具体的な型が見えない**」という属性を与える。

  ```yulang
  my f(g): [io] _ = g 10    // 許される。g が何を出すか、まだ分かっていない
  ```

  具体的な effect が見えていて、それが注釈に入っていなければ**エラー**になる。

  ```yulang
  // g に _ -> [undet] _ が入っていると分かっている場合 → エラー
  // 本体に明白な undet::choice [1, 2] がある場合       → エラー
  ```

- 期待: 共変位置の注釈は、見えている具体的な effect を縛るが、見えていない部分（行変数）は縛らない。
  `io` などは暗黙には入らず、書いたものだけが許される。
- T2 との対比: 反変位置では「引ける」属性、共変位置では「具体的な型が見えない」属性が、同じ書き方で位置によって変わる。
- 要確認:
  - 「具体的な型が見えない」変数が、あとで具体化して注釈に入らない effect だと分かったときの扱い（その時点でエラーか、推論の終わりまで待つか）。
  - 反変位置の属性と共変位置の属性が、同じ変数に両方付いた場合。
- 関連: 章5 effect と handler、章7 型の表示、`main:notes/design/2026-07-03-hover-public-type-projection.md`、`main:notes/debugs/std-var-ref-effect-annotation.md`

### T4. pattern の位置の修飾なしの名前は、variant ではなく新しい束縛になる
- 状態: 要確認（素材から起こした）
- 現象: `case c: red -> ...` の `red` は、同名の variant があっても何にでも合う新しい変数になる。以降の arm は到達しない。
  `color::red` と修飾するか、`use color::*` が要る。
- 関連: [章3b](03b-patterns.md) 3b.2

### T5. `0..10` は閉区間
- 状態: 確定（意図した仕様, 2026-11-04）
- 現象: `for x in 0..10:` は 11 回反復する（0 から 10 まで）。半開区間は `0..<10`。
- 関連: [章3c](03c-control.md) 3c.1

### T6. `cast` 宣言と `Cast` role は別物
- 状態: 確定（同名は意図的、変更予定なし, 2026-11-04）
- 現象: `cast(x: A): B = body` は暗黙変換の規則を登録するだけで、標準ライブラリの `Cast` role を実装しない。
  `x.cast` という method 呼び出しも挿入されない。
- 関連: [章6](06-roles.md) 6.5
