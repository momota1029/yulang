# 罠台帳

直感と違う挙動、仕様と表示・実装の乖離を書き留める。ユーザーが随時足す。
各項目は「何が起きるか → どちらが正か → 状態」を書く。正しさの判断はユーザーが行う。

## 書式

```
### <短い名前>
- 状態: 確定 / 要確認 / 未定
- 現象: <最小の .yu 例と、実際に起きること>
- 期待: <言語として約束したいこと>
- 乖離の原因: <分かっていれば>
- 関連: <章 / 出典>
```

## 項目

### T1. effect 行の区切りは `,`（`;` は廃止）
- 状態: 確定（ユーザー説明, 2026-11-04）
- 現象: 旧表記と新表記は次のとおり。

  ```text
  旧: 'a [undet; 'b] -> ['b] list 'a
  新: 'a [undet, 'b] -> ['b] list 'a
  ```

  行の中の effect と行変数（`'b`）の区切りは `,` だけを使う。`;` は廃止された。
- 期待: 仕様・例・表示のすべてで `,` を使う。
- 注意: main の既存文書（`web/docs`、`spec/`、`notes/` など）には旧表記 `;`（例: `[var<α>;]`）が残っている。素材から起こすときは新表記に直す。
- 閉じた行と開いた行の区別（確定, ユーザー回答 2026-11-04）: 記法としての区別は、**行変数が生で（明示的に）書かれているかどうか**だけ。
  `[undet]` のように変数を書かなければ閉じた形式、`[undet, 'b]` のように変数が出現すれば開いた形式の表記になる。
  `;` による区別はもう無い。
  - 要確認: この区別が型の表示（章7）でも同じ意味で使われるか。注釈で閉じた形式を書いても、実際に採用されるのは開いた形式になる（T3）。
- 関連: 章1 字句、章5 effect と handler、章7 型の表示

### T2. 反変位置の effect 注釈は「引いてよい」を意味する
- 状態: 確定（ユーザー回答 2026-11-04）。例の細部は要確認
- 現象: 引数の型注釈の中の `[undet]` は反変位置にある。

  ```yulang
  my f(g: 'a -> [undet] 'b) = ...
  ```

  ここでの `[undet]` は「`g` はちょうど `undet` を起こす」という固定ではなく、
  「**`undet` を引いてもよい `'c`**」と解釈される。許可であって義務ではない。**引かなくてもよい。**
- 推論結果の例: 通常の推論では `f` の中で実際に `undet` が引かれることがあり、たとえば次のようになりうる。

  ```text
  ('a -> [undet, 'd] 'b) -> 'a -> ['d] list 'b
  ```

  引数側の行は `[undet, 'd]`、結果側の行は `undet` を引いた残り `['d]` になる。
  注釈に書いた `[undet]` が、結果の型に「そのまま」残るわけではない。
- 複数書いた場合: `[undet, io]` は「`undet` か `io` を引いてよい `'c`」と解釈される。両方を引く必要はない。
- `undet` 以外の effect を渡してもよい:

  ```yulang
  // g に var 'b を持つ関数を渡してもよい
  ```

  このとき `'c = var 'b` になる。ただし、高階関数 `f` の中で `var 'b` を引こうとしても**引けない**
  （`f` が引いてよいと宣言したのは `undet` だけ）。
- 期待: 反変位置の `[...]` は「その effect を引いてよい余地」を表す、という読み方を仕様として固定する。
- 要確認:
  - `'c` は上界の制約ではない（ユーザー回答）。では何として導入され、どの量化境界で束縛されるか。
  - 「引けない」場合に何が起きるか（型エラーか、引かずに通すか）。上の `var 'b` の例を実際の `.yu` と出力で確かめる。
  - 引かなかった場合（実際には `undet` が起きない `g` を渡した場合）の推論結果の型。
- 関連: 章5 effect と handler、`main:spec/2026-05-31-effect-variable-subtractable.md`（directed stack weight）、`main:notes/design/handler-row-subtraction.md`

### T3. 注釈は閉じた形式で書き、採用されるのは開いた形式。共変位置では書いていない effect を足さない
- 状態: 確定（ユーザー回答 2026-11-04）。例の細部は要確認
- 前提: 型注釈の effect 行は**閉じた形式**で書く（行変数を書かない）。
  実際に採用されるのは**開いた形式**で、高階関数が絡む場合の型変数を省略した書き方になっている。
- 現象: 共変位置（たとえば関数の戻り値側）に `[undet]` 系の注釈を書いた場合、次の二つが成り立つ。
  1. **明示した effect だけが入る。** 注釈に書いていない `io` などは、暗黙には入らない。
  2. **共変位置の `[undet]` は開いた行として扱われる。** 注釈に変数を書かなくても、表示された型に
     行変数（`'a` など）が生で出現してよい。これは誤りではない。
- 期待: 共変位置の注釈は「列挙した effect を含む」ことを述べ、他の effect を暗黙に足さない。
  行が開いているので、変数が表示に出ても仕様どおり。
- T2 との対比: 反変位置では `[undet]` が「引いてよい行」になり、共変位置では「この effect を含む（開いた）行」になる。
  同じ書き方が位置で意味を変える。どちらも注釈は閉じた形式で書く点は同じ。
- 要確認:
  - 「注釈と表示型の乖離」として利用者が驚く具体例（注釈 → 実際の表示）を足す。
  - 「高階関数が絡む場合の型変数を省略した形式」の正確な規則（どこに変数が補われるか）。
  - `main:notes/debugs/std-var-ref-effect-annotation.md` の「型引数注釈の effect 行が畳まれない」例との関係。
- 関連: 章5 effect と handler、章7 型の表示、`main:notes/design/2026-07-03-hover-public-type-projection.md`
