# アイデア: bounds の伝播を Simple-sub より安くする (2026-11-07)

状態: **ユーザーの着想。検証前。** ユーザー自身が「勘がどこまで当てになるか分からない」と言っている。決定も設計も無い。
署名: 着想はユーザー。整理は Claude (Sonnet 5.5)。

## 背景

Lean の核は、推論を `Formula` とモデルで特徴づけた同値の定理が中心で、solver の部品（飽和・worklist）は参照実装（`spec/10`: 「列挙型の参照実装であり、性能上の主張ではない」）。
Simple-sub のような、効率のよい算法と核をつなぐ定理は無い。そのまま Rust に書けば、素直なグラフ解法になって計算量が重い。
そのため、高速化と証明は切り離せない（oracle 計画 `2026-11-06-rust-oracle-plan.md` §6 は、性能設計を書いたが、実装も測定も無いと明記している）。

## ユーザーの着想（言われたまま）

- Simple-sub よりも高速化できる可能性があると考えている。伝播は、もう少し効率化できる気がする。
- 変数同士の比較は、union-find のようなもので、上界や下界を**まとめる操作**にしてしまえると思っている。
  単一化の観点から、まとめる動作にはできるはず。
- エフェクト変数も、Simple-sub の上界・下界の解法が、ほぼそのまま使える。やっていきたい。
- 自分の勘がどこまで当てになるかは、分からない。

## 私の整理（未検証。着想の点検用）

1. **何をまとめるか。** 「変数」を一つにまとめるのか、「bound の集合」を共有するのかで、意味が変わる。
   `α ≤ β` の変数を一つに潰すと、`α = β` を課すことになり、一般には精度が落ちる（`α ≤ β` は `α = β` ではない）。
   潰して正確なのは、輪になるとき（`α ≤ β ≤ α`、強連結成分）だけ。
   点を指す解析の「単一化ベース（Steensgaard 流、ほぼ線形、粗い）」と「包含ベース（Andersen 流、精度が高く重い）」の関係に似る。
   着想が前者に寄るのか、後者の集合を共有する形なのかを、先に決める必要がある。
2. **bound 集合の共有。** 下限 `L(α)` を `β` の下限へ流す伝播は、集合の和。和を遅延・共有で表せば、閉包を作らずに済むかもしれない。
   これは union-find よりも、融合可能な構造（共有する木、持続的な集合）に近い可能性がある。
3. **effect 変数。** 行は和（join）で集まるので、上下の bound が自然に使えそうだが、
   Yulang には handler による行の引き算（stack weight、mask、衛生性。`spec/05`、`spec/10` 10.3）がある。
   「ほぼそのまま」が成り立つかは、引き算を含む場所（handler の境界）を見て確かめる必要がある。
4. **評価の方法。** 算法を Lean の関数として書き、いまの参照実装（と、その下の `Formula` の意味）の洗練（refinement）であることを証明する。
   性能は、oracle 計画 §6.6 の最初の benchmark の条件で測る。着想の良し悪しは、両方で判定する。

## 未決（ユーザーの判断を待つ）

- この算法の設計と証明を、誰に任せるか（ChatGPT Pro を想定。M1 の後）。

## 追記 (2026-11-07 夕): 型を伝播する必要は、究極的には無いのでは

状態: **ユーザーの着想。検証前。** ユーザー自身が「どこまでうまくいくかは分からない」と言っている。
署名: 着想はユーザー。整理は Claude (Sonnet 5.5)。

### ユーザーの着想（言われたまま）

- union-find の話を思いついた。型を伝播する必要は、究極的にはないのではないか。
- 型を具体化するとき、上界と下界でそれぞれ mono 化する必要があり、そのときに型検査をすればよい。
- 「今回は起きない型警告」と称して、並列でエラーを出せばよい。
- 型を集めてくるときに、上界や下界は個別に計算するので、それで十分。
- どこまでうまくいくかは分からない。

### 私の整理（未検証。着想の点検用）

**読み方。** 変数ごとに上界の集合と下界の集合を持つが、`α ≤ β` の辺を越えての**閉包は作らない**。
具体化（mono 化）の時点で、各変数を極性に従って下界（正の位置）か上界（負の位置）の具体型に決め、そこで下界 ≤ 上界を検査する。
一般化の時点で決められない不整合は、定義側ではエラーにせず、「この具体化では起きない型警告」として並列に報告する。

**得られそうなもの。**
- 閉包（下限 × 上限の積）を、一般化の時点で作らずに済む。
- module scheme の cache（`2026-11-06-rust-oracle-plan.md` §6.1）と相性がよい。標準ライブラリは、使われた具体化だけを検査すればよい。
- 近い設計に、制約を scheme に残す qualified な型（HM(X) 系）がある。核にも `CoreQualified`（role の制約）の前例がある。

**確かめたい点。**
1. **伝播は消えたのか、移ったのか。** 具体化の時点で、内部の変数（interface に出ない変数）の値を決めるには、辺を具体型の上で辿ることになる。
   つまり、記号的な閉包を、具体化ごとの地上型の伝播に置き換える形になる。総費用が下がるかは、具体化の回数と、記号的閉包の大きさの比で決まる。
2. **地上の制約はその場で検査できる。** 下界も上界も具体型なら、`int ≤ str` のような不整合は、定義側でも即座に分かる。後回しにするのは、interface の変数を含む制約だけ。
3. **公開定理の形が変わる。** 前回の依頼では、返した scheme の任意の parameter が `ResidualHolds` などの残余条件なしに Models を与えることを要求した（7.2・7.3）。
   制約を scheme に残す案は、「制約を満たす parameter」に限る形になり、この定理の形を変える。核の仕様判断（ユーザー）。
4. **effect の引き算。** handler が行から operation を引く規則（stack weight、mask）は、単調ではない。具体化まで引き算の結果が決まらない型を、どう表示・検査するか。
5. **診断と表示。** エラーが使用側の具体型で出る。定義側への「なぜ」の遡り（provenance）と、hover に出す簡約した型は、別に必要になる。
6. **具体化の数。** C++ のテンプレートのように、具体化ごとに検査すると、数が増えうる。具体型の組で cache する必要がある。

## 訂正と追記 (2026-11-07 夕): 伝播の計算を遅延する（評価戦略の話）

状態: **ユーザーの着想。検証前。** 上の「型を伝播する必要は、究極的には無いのでは」の節の私の読みは、取り違えだった。
署名: 着想はユーザー。整理は Claude (Sonnet 5.5)。

### ユーザーの意図（言われたまま）

- 上界・下界の伝播の計算を**遅延する**という話のつもりだった。
- 計算できるところだけ計算してしまえば、計算量はかなり減るのではないか。
- 実際に実行するところ以外の型エラーは、もっと遅く出しても文句は言われないのではないか。
- たとえば、ライブラリ自体の型検査を、実行前にはほとんど行わない。遅延かつ並行で、実行とともに型検査ができるようになっていく。
- レスポンスを早めるための工夫。

### 訂正

直前の節の「制約を scheme に残す」という読み（qualified な型）は、この意図ではない。遅延は**何が導けるかを変えず**、いつ計算するかだけを変える。
したがって、公開定理の形（任意の parameter が残余条件なしに Models を与える、など）は変わらない。変わるのは、solver が結果を出す順序と、出すタイミング。

### 私の整理（未検証）

**型に導かれる実行がある。** 実行そのものが、型から決まる elaboration を使う（role の辞書の選択、`cast` の挿入、handler の宣言と衛生性、junction、`xs[i]` の error effect）。
実行する関数の elaboration に必要な型は、実行前に決める必要がある。遅延できるのは、**実行しない部分の型**と、**不整合を報告するための検査**。

**要求駆動（pull）の solver。** 変数 α の bound が必要になったときに、α に流れ込む辺だけをさかのぼって計算し、結果を memo する。全体の閉包は作らない。
言語サーバー（hover が型を問う）にも、そのまま使える形（`2026-11-07-error-tolerance-status.md` の部分推論の課題と同じ土台）。

**案: 最初の呼び出しの前に検査する。** 関数を最初に呼ぶ前に、その SCC の型を決めて検査する（memo）。実行する経路は、実行の前に必ず検査される。実行しない部分は、バックグラウンドで後から検査し、「今回は起きない型警告」として並列に報告する。
これなら、「実行したコードに型エラーが残る」ことは無く、起動も軽い。標準ライブラリの大半は、スクリプトが触らないので、検査されないまま済む。

**確かめたい点。**
1. 呼び出しの到達可能な範囲が、実行前に決める必要のある型の範囲。注釈の無い関数は、本体を推論しないと型が分からないので、到達可能な全体を推論することになる。高階関数や role 経由の呼び出しは、到達の範囲が広がる。
2. 実行と並行に走る検査の状態の共有（solver の可変状態）。SCC 単位で隔離できるか。
3. 遅れて出るエラーの出し方。短時間で終わるスクリプトは、終了時に待って報告するか。`yulang test` や CI は、全部を検査する（eager）モードが要る。
4. **証明の側。** 遅延 solver の結果が、eager な solver と、問われた node で一致すること（要求駆動の計算が、その node に流れ込む全ての辺をさかのぼること）を示す。これが、算法の洗練（refinement）の定理になる。全体の検査が最終的に済めば、`rejected` の判定も eager と一致する。
5. 実行の副作用が、後から見つかる型エラーより先に起きうる範囲（実行しない部分のエラーは、そもそも実行に影響しない）。

### 決定 (ユーザー, 2026-11-07): 実行する経路の検査は、実行の前に済ませる

ユーザーの言葉: 実行する経路の検査は、実行の前に済ませる。それが型推論だから。型が決まらないと method などが決まらず、実装が決まらない。ここは伝播を eager にするべきところ。

整理（Claude）:
- **eager にする所 = 実装の選択が型に依存する所**。method の解決、role の辞書の選択、`cast` の挿入、handler の宣言と衛生性、junction、`xs[i]` の error effect。
  これらの node が、solver への「要求の根（demand root）」になる。根が問う変数の bound を、さかのぼって eager に計算する。
- **遅延する所 = 根が問わない所**。実行しない関数、実行しても根から問われない変数の bound、不整合を報告するための全体の検査。バックグラウンドで後から埋め、「今回は起きない型警告」として並列に報告する。
- 粒度は関数（相互再帰なら SCC）。実行する関数の中の、通らない分岐も、その関数の型としては決める。
- 前の節の確認点 5（副作用が後から見つかる型エラーより先に起きうるか）は、この決定で解消する。実行した経路は、実行の前に検査されている。
