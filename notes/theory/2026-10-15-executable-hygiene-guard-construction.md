## 3. Finite transfer proposal

Use the existing colored-core weight algebra, with a fresh static boundary id
`u = (original omitted-formal seed, original Apply a)`, seed capability empty,
and the retained original Lambda `L` as the proposed receiver owner descriptor.
This tuple is a proposed source key, not a claim that the current compiler
already allocates the id. Distinct original Applies retain distinct ids even
when their row coordinates become equal.

For one id, represent an entry by `(p,q,F)` and compose left-to-right:

```text
(p,q,F) odot (r,s,G) = (p+r-t, q+s-t, F intersect G)
t = min(q,r)
g_u = (0,1,All), seed(u) = empty
p_u = (1,0,All)
g_u odot p_u = identity
p_u odot g_u = (1,1,All), which is not identity
```

The transfer rules are:

1. At the authentic slot-2 invocation-to-Apply-output connector, add the
   positive view `g_u(Eout)`. Do not change the original provider output, the
   Function demand's other ports or the callee-evaluation slot-1 connector.
2. Ordinary forward propagation composes normalized weights in source order.
   Store the context on the bound and replay it against both existing and
   future opposite bounds. Memoization includes the normalized weight and
   original contribution/owner evidence; a raw row pair is insufficient.
3. At a Catch, compute the eligible head separately for each actual incoming
   contribution: `J = K intersect Common(flat(L,R))`. With active `g_u` and
   empty seed, `Common` is empty, so this contribution is forwarded unchanged.
   Ordinary eligible contributions still use their own residual and `L minus J`.
4. At the original receiver's outward body-result edge, append matching `p_u`
   for every installed id belonging to that receiver. For the protected path,
   `g_u;p_u` cancels. A local contribution with no `g_u` has a leading pop;
   operationally its matching push is in the enclosing owner frame, outside
   that contribution's provenance fragment. Do not reject this local path or
   infer that its effect was protected inside the owner.

An owner can have finitely many such static ids, discovered while constructing
its source demands; unconditional owner-frame installation for an unexecuted
branch creates no request color by itself. This is a finite transfer schema,
not a proved finite bound on recursive saturation or dynamic frame depth.
Sparse maps of normalized entries suffice per finite processing step; no
typing search or arbitrary-view registry is part of these transfers.

## 4. Concrete source and operational trace

This is a source-shaped discriminator, not an executed fixture or an asserted
inferred scheme. Operation-pattern syntax is witnessed independently in
`yu-hir/tests/catch_local_source.rs:82–105`.
In particular, the directional addendum §2 withholds a blanket result for
concrete provider events. The following guarded receipt/entry placement is a
candidate construction for that missing bridge. Its calculated result is
conditional on that construction; it is not already an expected Yulang output.

```yulang
act tick:
    our next: () -> int
my relay cb = catch cb() { tick::next(), k -> 0, v -> v }
my answer = catch relay tick::next { tick::next(), k -> 1, v -> v }
```

Fix original relay Lambda `L`, formal `cb`, upper Apply `a = cb()`, inner Catch
`Hi`, outer Catch `Ho`, and distinct original binders `ki,vi,ko,vo` (the source
spellings `k,v` resolve to distinct arm-owned identities). Both catches cover
the same resolved operation; matching family alone supplies no permission.

Here is an exact candidate materializer for that direct invocation route:

```text
enter original receiving invocation ell of L:
    choose fresh color c for u in this owner instance
    Xi := support(Phi)                    // before this owner's push
    push c in Phi                        // owner frame, not a whole-body guard
    install the output guard recipe (a,u,c,empty,Xi) at original Apply a

execute a:
    execute the original cb call, retaining its payload and continuation
    pass its output through Guard[c,empty,Xi]
    send that output into the surrounding source context, including Hi

search/return crossing ell's original outward delimiter:
    pop exactly this owner's c
    pop-paint the escaping outcome, value, payload and continuation
    continue outward search, including Ho
```

The guard recipe does not wrap the callback provider's original body with a
new Catch or mutate its lower effect row. Its operation is precisely the
original colored-core outcome transformer:

```text
ret V             -> ret guard(c,empty,V)
op(h,kappa,V,K)    -> op(h,kappa',guard(c,empty,V),
                         lambda x. Guard[c,empty,Xi](K x))
kappa' = kappa union {c}  if kappa intersect Xi = empty
         kappa           otherwise
```

Freshness gives initial `c` absent from the outer flow. With no outer colors,
the callback's `tick` request starts with `kappa=empty`, obtains `{c}`, and Hi
sees `c` active: Hi forwards. Search exits ell, removes `c`, and paint retains
`{c}` on the request. Ho now sees `{c}` disjoint from the outer flow and can
proceed with its ordinary arm checks. This visibility calculation does not
assert that every generic arm is typeable or that Ho necessarily selects it.

If a separate ordinary `tick` contribution is emitted directly by relay's
body, it does not cross a's output guard. Its colors remain empty, so Hi can
consume it even while `c` is active. Static paths are respectively `g_u` and
identity at Hi, then respectively identity and `p_u` outside ell. If Hi consumes
only that ordinary contribution, the protected contribution still survives.
Thus neither a support-wide family deletion nor a row-wide protection bit
implements this trace. A source-shaped variant exposing both contributors is
`catch (if flag { cb() } else { tick::next() }) { ... }`; inference retains both
branch contributions without evaluating `flag`. That variant illustrates the
required union, not a claim that one sequential run emits both requests.

## 5. Conditional invariant and two falsifiers

Assume this materializer supplies original owner entry/exit and the original
callback output route, with well-bracketed normal/search exits and continuation
re-entry, as required by the Oracle lemma. The essential invariant is:

```text
While ell's receiving frame is live, exactly its installed frame contributes
one active count of c; only the original guarded invocation-output routes add
c to requests. Xi contains only colors active before ell's push and remaining
active throughout this live interval. Every crossing of ell's outward delimiter
removes its count; all escaping paths retain the prescribed paint/guard data.
```

For any operation crossing this route and any family h, h is outside the empty
capability. If its old colors miss Xi, the exact guard transformer adds c, and
`c` is active at Hi. If they meet Xi, a pre-existing outside color hides it,
and the invariant keeps that color active throughout this interval. These are
exactly the two cases of Oracle `lem:one-color-hygiene:1665–1680`; no statement
about arbitrary typed views is needed for this calculation. Other contributions
are unchanged because this guard is applied only at a's output route. At owner
exit c has no active count, so c alone cannot hide the escaping operation.
Other still-active protections remain effective. This establishes the stated
conditional direct-route visibility property, not global hygiene or principality.

Two tempting shortcuts fail on concrete distinctions:

1. **Only a callback-call frame.** If push/pop surround `cb()` and pop before
   the enclosing Hi tests its request, c is already inactive at Hi. The source
   above distinguishes this from the required owner-lifetime behavior.
2. **A guard on every relay-body outcome.** This paints relay's independent
   ordinary `tick` contribution as well as cb's contribution. The `flag` variant
   distinguishes this from guarding only the selected upper-output route.

The snapshot also has a decisive constraint. Taking a new snapshot when cb is
called can include a color d introduced *after* ell's entry. A request already
colored d might then skip c, and after d's inner frame is popped Hi could see
it. Xi at the original owner entry excludes such later colors, so c is added.
This is precisely why current invisibility or a late arbitrary snapshot cannot
replace the lemma's lifetime-compatible entry snapshot.
