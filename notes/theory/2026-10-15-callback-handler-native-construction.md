## 3. Construct the two owners and the three original paths

Keep the following owners distinct:

| Source owner | What it actually owns |
| --- | --- |
| outer application u | Host callee/whole callback-argument construction and its operand tuple; constructing L is inert. |
| host activation r receiving L at slot β | Original received callback view `V_(r,β)` and its β profile; the receipt of the callback value, not receipt of L's future argument. |
| latent activation ell of L through that slot view | Whole argument carrier D, L's own syntax-directed argument receipt, designated Force, rebind, body and result-consumer suffix in `X_latent`. |

The original profile boundary instance is

```text
b_(r,β) = (r, β, Γ_β, original type endpoints).
```

This is typed-boundary §6's existing boundary parameterization. Generation uses
a symbolic activation parameter r; constructing L allocates no live r or ell.
Each actual source invocation supplies its activation/receipt through the
existing core rules. It does not turn a static source scope id into r or b.
The receiver role of newly introduced L and the host's typed slot view have
different responsibilities: the former is selected before body generation;
the latter governs actual invocation through that slot. A prebuilt Pure value
would keep its introduction role, so slot-view construction alone cannot prove
the new-literal Handler introduction rule.

For unannotated L's parameter x, source syntax constructs `Value(A)` with fresh
A, independently of F_cb. Its latent entry skeleton is exactly

```text
Invoke ell with actual D;
establish ell's argument receipt;
Force_argument(D) >>= (a,current_state =>
  Rebind x:Value(A);
  Run normalized body Result(I_body);
  ReturnFromInvocation).
```

For a Force-origin request q, the actual bind rule constructs

```text
Request(q,C,k_D) >>= suffix
  = Request(q,C, response,C' => k_D(response,C') >>= suffix),
suffix = typed rebind; original body; original return/result-consumer suffix.
```

Thus the request in the complete invocation is the *same* q, with the same
origin, response endpoint, continuation and pending suffix; it is not a newly
chosen effect-family witness. The original three paths are:

```text
d- : D's designated argument Force observation at J_arg;
d+ : that same Force-origin q/continuation, if exposed at complete J_call;
b+ : an original body/designated-result-consumer contribution,
     if exposed at that complete J_call.
```

The path from Force to complete invocation is generated by this bind/call
construction, not by equality of the entry and return rows. A divergent Force
does not reach b+; a retained path in a nested callable is opened only at its
actual later source use. An inner handler may consume a body request before
it is exposed at the callback's public CallView. No unconditional stamp on all
body requests or every slot-4 edge follows.

Let `G_L^Θ` be that existing source-generated latent invocation relation, with
the independent parameter/body endpoints and original tuples. For each complete
joined witness w of that relation, define

```text
Π_L^Θ(w) = ( P(w),
             π_d-(w),
             flat_joined_view(π_b+(w),π_d+(w)),
             Result(I_body)(w) ).
```

This is the source-indexed §6 completion equation. `flat_joined_view` keeps the
two tagged sources in w; it is not the product of their existentially hidden
marginals. Contravariant concrete structure at d- uses only the supplied actual
descriptor/attachment and existing subtraction evidence. Empty effect support
is not role, challenge admission or termination evidence.

This construction supplies the original source path from d- to d+ explicitly;
it does not yet identify `Π_L^Θ` with a native row or native least solution.

callback value. Only source-justified profile positions are included: a


No explicit permission means no Grant, even though the applicable position is

For each of d+ and b+, the actual source trace derives its observation at the
same complete executing slot view when, and only when, that exposure is reached.
The existing receive/flow rules therefore give the following exact equation:

```text
Path(q, owner(h), b_(r,β), p)
  iff the original β position p reaches the actual exposed effect path
       in the same slot view by the source-generated typed flow,
       Observe(q, that executing view, that path) holds,
       and owner(h) receives that same view along that typed correspondence.

Inc_C(q,h,b_(r,β),p)
  iff that Path and Active(h,C) and Active(owner(h),C) and Active(r,C).

Grant_C(q,h,b_(r,β),p)
  iff that Inc and r=owner(h) and Γ_β(p) explicitly admits q.operation under ν.
```

Proof at this local source node: r's receipt comes from the host's actual
parameter binding; invoking its formal opens that same received slot view.
The Force bind above supplies q unchanged at the call exposure, or the body
source constructor supplies its own actual escaped request. Following the
original typed path yields precisely the displayed Observe/Flow witnesses;
substituting them into typed-boundary §6's definitions gives both directions.
Conversely an incidence must have those same original profile, observation,
receipt and active-owner witnesses by definition; another alias, family or
activation cannot fill them. Re-entry does not replay receipt or revive an
expired owner. This is a local constructor derivation, rather than assuming
that an arbitrary native row transition already supplies those witnesses.

The outer host receipt of L is not ell's inner receipt of D. Moreover ell does
not receive its own public callee view merely by being invoked: L's body starts
from its actual parameter and captured bindings. Therefore its own local
handler can handle an ordinary direct body request unless those actual inputs
independently impose protection. The equation agrees with typed-boundary §6's
receiving-side consequence; it does not blanket-protect L's private body.
