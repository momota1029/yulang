## Candidate routing audit

The current solver path cannot consume these carriers by adding only a Member branch to `emit_candidate_source`. Candidate collection visits ordinary `HirItem` roots and selects Definition or Expression owners. `emit_candidate_source` likewise authenticates only those two parent/owner pairs, and its final publication creates a Definition schedule or an Expression schedule; a Member body would otherwise have no retained schedule. `CandidateValueGraph::retain_source` explicitly refuses `SourceRootId::Member`, because its vertices have only Module, Local, Parameter, CatchBinder and Expression values. Candidate scheme publication is keyed by Definition roots and executes on the enclosing definition SCC.

The carrier also currently passes an empty parameter list and extracts only the RHS. This is intentional source recovery, not a claim that member header binders are in scope. The member body must remain deferred until the original FieldTail receiver's exact value/effect rows settle; then the selected implementation body must be checked against the corresponding role member signature. ## Operator and tuple-pattern consumer audit

Followed the exact `Display.say` `+` occurrence through the current parser/HIR seam (`yu-hir/src/lib.rs::hir_operator`, `yu-syntax/src/operator_table.rs::OperatorOrigin`, `syntax_environment.rs::SyntaxDependencyProvenance`, and `yu-hir/src/module/source_exports.rs`). `ParsedFile` retains the effective `OperatorTable`; the operator associator uses its binding powers and emits `HirExpr::Apply` with a `HirOperator`. That HIR operator retains only spelling, fixity and occurrence range. The source-level table origin is only `Local` or `Imported(SyntaxDependencySlot)`; imported syntax provenance identifies a module label and revision, not the operator value declaration. `SourceExportIndex` currently records module/type/enum/role/act/binding declarations and has no operator-value identity. Therefore converting this expression to ordinary `LocalSourceForm::Apply` requires an additional authenticated link from the parsed operator occurrence through the syntax dependency/import route to the declaration whose value implements that operator. Mapping `+` to `x.add y` would only be valid for a separately established specific declaration and is not a general operator rule. The target body currently has no such link.

The tuple-pattern obstacle also reaches beyond parsing. Before this iteration, `LocalSourceCasePattern` contained only Integer, Binder and Wildcard, and candidate setup mapped each CaseBinder directly to the entire scrutinee endpoint. For `(a, b)`, the candidate input must instead constrain the scrutinee against an ordered negative tuple whose component rows become the binder endpoints. Existing tuple expression admission already constructs ordered positive tuple terms and solver tuple matching decomposes positive/negative tuple bounds, so that is the nearby mechanism to extend. Merely retaining two binder spellings while aliasing both to the whole tuple would be wrong.

This audit narrows the next implementation seam to two source-to-candidate bridges: authenticated operator value resolution, and ordered tuple-pattern component rows. It supplies no body typing or proof. The R303 exact lease has no `yu-syntax` paths, so changes that require new parser/source-dependency fields must first be routed through the next authority boundary; in-scope HIR and solver work can still proceed using existing parse provenance and tuple terms. The unchanged samples and all proof gates remain open.
