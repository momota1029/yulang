## Admission timing, queue ownership and actual discharge

Newly admitted `candidate_intrusion::mark_candidate_pair:423–455` canonicalizes
the task, records the current processing relation only for a raw canonical key,
journals the old completion value when a route transaction exists, and writes
`completed[relation]=generation`. Its caller is
`lib::record_typed_pair_admission:13145`. In the actual Function branch this call
occurs at :12710 **before** FunctionDispatch installation at :12728 and before
any port admission at :12835–12861. The memo itself says DiagnosticCompletion::Pending.
Consequently completion-map membership alone is not a four-port-consumption
certificate at an arbitrary prefix. This is a source control-order separation,
not a demonstrated reachable whole-source counterexample or a solver error.

The following narrower local conservation follows by induction over the actual
FunctionAdmission/FunctionEnqueue transitions. Initially `next=0,pending=None`
owns all four children. Admission creates precisely the next pending item.
Only successful enqueue clears pending and increments next; failures do not
advance. The exact admitted relation is passed to enqueue_item, which retains
it (:13028–13051); pop_worklist journals and transfers the actual front item
(:12971–12976). Transport retains it as current; Context runs before Dispatch
(:12375–12471). A successful no-rollback segment cannot finish its Function stage
before all four transfers. Diagnostics is entered only after current/function
work finishes, the queue is empty and intrusion is clean; acknowledgements
precede ReturnReady (:12761–12825). Thus within such a segment issued ports
are pending, queued, current or already **visited** by Context/Dispatch, and a
successful drain does not merely abandon issued ports. This proves local
ownership/visitation, not semantic discharge for a skipped/reused port.

The further in-envelope audit inspected the following transitions instead of
assuming they preserve a stronger invariant:
