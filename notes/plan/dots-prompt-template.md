dots は計画表への状態書き込みを拒否されることがあるが、無視してよい（状態更新は監督役が行う）。

```text
GitHub の momota1029/yulang リポジトリ(https://github.com/momota1029/yulang)の integration/m1-final ブランチで、Lean の証明を一つ、実際に進めてください。これは本番の作業です。

最初に integration/m1-final の最新を取得し、notes/plan/README.md と notes/plan/m1-plan.md を読み、その「{ID}」({ONE_LINE})を担当してください。共通の前提として挙げられた文書と、そのタスクが「参照」に挙げた文書、関係する質問ノート(notes/questions/)を読んでから始めてください。計画表の状態を書き換える権限がなければ、書き換えずに続けてください。

進め方:
- 作業はあなたのクラウド PC のクローンの中で行い、小さな単位(補題一つ・定理一つ)ごとにローカルで commit してください。ビルドは `cd lean && lake build --wfail`、全体の検証は `bash tools/verify-lean.sh . origin/integration/m1-final` です(既存の PASS 結果と同じ形で、REVIEW の行は人が読みます)。
- 新しいコードは lean/Yulang/ の新しいモジュールに書き、既存の Lean ファイルは変更せず、lean/Yulang.lean・lean/Audit.lean・lean/README.md にだけ追記してください。新しい主要定理は Audit.lean に登録してください。sorry、新しい公理、native_decide は使わないでください。既存の定理を弱めないでください。spec/ は編集しないでください。lakefile は、新しい lean_lib の追加が本当に必要なとき以外は変えないでください。
- 設計の判断が要る点(spec が黙っている点、複数の選択肢がある点)は、決めずに、Yulang の例つきで質問ノートを notes/questions/ に1本書き、決めずに進められる部分を続けてください。意味論はユーザーの設計判断です。選択肢は、遅延する案を先頭に書いてください。
- 設計を先に: 大きな Lean を書く前に、データ、独立な宣言的判断、実行版、証明する定理の型(量化子つき)を notes/design/ に短く書いてください。上から作り、外側の定理が仮定を持つなら、その仮定を名前つきで明示してください。狭くて本物の断片を決めて、その上で仮定なしの定理にするほうが、広い目標を部品の足し算で追うより良いです。
- E2(反例)が出ても、そこで終わりにしないでください。反例を除く定義を設計し直して、証明まで進めてください。
- 結果の公開: push はできないので、GitHub アプリ経由で work/dots-{ID} ブランチに、変更・追加した全ファイルを公開してください。30〜40分ごとと、完了時に、その時点の全変更ファイルを公開してください(途中で環境が落ちても、公開済みの分から再開できるようにするためです)。integration/m1-final など他のブランチには書き込まないでください。
- 最後に報告ファイル notes/handoff/2026-11-08-dots-{ID}-results.md を同じブランチに公開してください。内容: 実行したコマンドと結果(verify-lean.sh の出力全文)、追加した定理の名前と日本語で読める主張(量化子と前提を省かない)、受け入れ条件のどれが達成されたか、確かめていないこと、残りの補題、公開できたファイル数、途中で起きた中断や制限、全体の所要時間。

達成の基準は、計画表のそのタスクの「受け入れ」です。達成できなくても、どこまで進み、何が残っているかを正直に書いてください。できなかったことを、できたと書かないでください。
```
