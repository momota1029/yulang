# 計画表の運用 (2026-11-08)

`m1-plan.md` が、M1 の残りの仕事の計画表。作業者（ChatGPT Pro、Codex の Terra/Sol/Astra、dots など）は、
この表と、そこから参照される文書だけで、仕事を取って進め、結果を戻せる。会話の記憶には頼らない。

## ループ

1. 起きたら `origin/integration/m1-final` を取得し、`m1-plan.md` を読む。`状態: running` で 45 分以上更新のないタスクは、停止とみなして `todo` に戻してよい。
2. `状態: todo` で、依存が `done` のタスクを一つ選ぶ。選んだら、状態を `running`、担当と時刻を書いて、**その編集だけの commit** を push する（取り合い防止）。
3. 作業は専用の branch `work/<タスクID>` で行い、小さな単位（補題一つ・定理一つ）ごとに push する。`integration/m1-final`、`yulang3`、`integration/types` には直接 push しない。
4. 終わったら、結果の報告を `notes/handoff/<日付>-<タスクID>-results.md` に書き、状態を `needs-verify` にする。報告には、実行したコマンドと結果、証明した定理の名前と日本語で読める主張（量化子と前提を省かない）、確かめていないことを書く。
5. 検証は監督役（または検証用の定期ジョブ）が `tools/verify-lean.sh` で行い、通れば統合して `done`。通らなければ理由を書いて `todo` に戻す。
6. 設計の判断が要る（spec が黙っている、複数の選択肢がある）ときは、決めずに `notes/questions/` に 1 問積んで、状態を `needs-owner` にし、決めずに進められる部分を続ける。選択肢は Yulang の例つきで、遅延する案を先頭に置く。

## 守ること

- 意味論はユーザーの設計判断。作業者は決めない。
- `sorry`、新しい公理、`native_decide` を使わない。既存の定理を弱めない。既存の Lean ファイルは変更せず、`Yulang.lean`・`Audit.lean`・`README.md` に追記する（新しい主要定理は Audit に登録）。
- 「証明できた」と「正しいものを証明した」を分ける。外側の定理が未証明の仮定を持つなら、報告にそう書く。
- `spec/` と `notes/plan/` の状態欄以外は編集しない（spec の変更はユーザーの決定の後に監督役が行う）。
- 落ちても再開できるよう、状態は常にリポジトリに置く。会話の中だけに残さない。

## 状態の意味

`todo` 未着手 / `running` 着手中 / `needs-verify` 作業者は終えた、検証待ち / `needs-owner` ユーザーの判断待ち / `done` 検証して統合済み / `blocked` 依存先が未完。
