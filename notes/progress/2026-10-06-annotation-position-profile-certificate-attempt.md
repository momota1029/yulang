## Minimal source shape and the distinction it requires

Use the exact approved example:

```text
apply(f: _ -> [io] _, x) = f x
```

Let `omega` be the annotation occurrence on `f`, and `sigma` its written
`io` suboccurrence. The result `_` is a hole in a written contract. It need
not be the final inferred result type. In particular, a completion may return
a callable `g`; this is a conditional completion, not a proved acceptance
claim for that source. The diagnostic future-use extension is `(f x) y`.

For a supplied decorated completion in which `f x` returns `g`, distinguish:

```text
J_arg(f,x)    whole received argument computation
J_body(f)     closure body's Result(I_body), if f is a closure
J_call(f,x)   complete invocation: actual receipt/entry/rebind/body/consumer/return
J_call(g,y)   later invocation of the actually returned callable
```

An inertly returned callable does not run when returned. For example, a
supplied provider derivation can request `io` before returning `g`, while
`g`'s own supplied body requests another effect `r` only on its later call.
The distinction requires one initial call and one latent returned callable;
no recursive source component, aliases, handlers or adapters are needed to
state it. The symbols `g` and `r` describe this conditional completion; they
are not extra annotations or operation declarations in the raw example.

There is a separate entry contribution even when the closure body simply
returns `g`: if `x`'s carrier requests an effect before yielding its value,
Value entry places that request in `J_call(f,x)` although `J_body(f)` is pure.
Typed-core §9 derives this distinction at the decorated-core level. It does
not supply raw annotation inference. Neither `[io]` nor the returned hole
justifies setting `J_body(f)=J_call(f,x)`, executing `g` during the initial
call, or computing the complete invocation by adding two support rows.
