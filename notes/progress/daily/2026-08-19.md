## Phase 2: parser recovery policy と header discovery

### yulang2 parser の調査

- ユーザーから「構文(parser)は yulang2 からサルベージできそうか」と問いがあり、
  main branch の `crates/parser` を調査した。tagged predictive NUD/LED dispatch と
  Pratt/precedence climbing からなる core algorithm は健全で、
  `docs/yulang3-architecture.md` §4.2.1 でも維持対象として明記済みだった。
- 一方で error recovery と diagnostic はそのまま移植できないと分かった。
  `parse_module_to_green*` は GreenNode のみを返して diagnostic を収集・公開せず、
  recovery marker は `SyntaxKind::InvalidToken` 一種類だけだった。
  `emit_missing_invalid` は複数 module に重複し、ユーザー向け diagnostic は
  `crates/yulang/src/source/mod.rs` が CST を再走査して構築する構成だった。これは
  architecture 文書が禁止する「bare CST + caller-side rewalk」に当たる。
- ユーザーの「エラーで回復できて十分にエラーを報告しきれるようになってほしい」という
  要望を受けた。Terra (medium) の調査で単純移植では済まない設計判断が必要と分かり、
  Sol (xhigh) へ検討を引き継いだ。

### Recovery policy と diagnostic completeness contract

- Sol は階層的な同期集合、3 段階の token 消費方針（挿入回復 = Missing、局所 Error、
  同期回復）を提案した。`Missing` は zero-width、`Error` は 1 byte 以上を消費するものとして
  厳密に区別する。
- episode 単位で複数 error を収集し、silent recovery を許さないこと、error との一対一対応、
  独立 error の収集、deterministic、lossless / balanced を観測可能な completeness contract とした。
- ユーザーの「文法・診断表示は yulang2 からできるだけ変えたくない」という方針に合わせ、
  `code: yulang.syntax` などの user-facing 表示は当面維持する設計とした。

### Header discovery を含む pipeline

- ユーザーの指摘で、依存関係を決める header parsing への言及が不足していると分かった。
  追加調査により、yulang2 の `parse_header_to_green` は leading `use` と dynamic operator
  header だけを読む軽量 prepass であり、`mod` と本文中の `use` は対象外、diagnostic も
  破棄していることを特定した。
- 設計を Header discovery (`HeaderInfo`) → Syntax planning
  (`SyntaxInterface` / `SyntaxEnvironment`) → Full parse (`ParsedFile`) → Resolve/Lower の
  4 段階 pipeline へ発展させ、syntax dependency と semantic dependency を分離した。
