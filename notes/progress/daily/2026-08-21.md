### use 宣言構文の誤りの発見と修正

- ユーザーから「`use path.component` なんて構文ないけど」という指摘を受け調査したところ、
  `tests/contracts/phase2-parser/v0/cases/leading-use-plain/main.yu` の fixture 自体が
  `use std.data` という誤った dot 区切りになっていたと判明した。yulang2-oracle の正規 path
  区切りは `::` と `/` のみで、`.` は使わない。同じ誤りは `malformed-header-followed-by-valid-header`
  と `late-use-after-body` にも残っていた。
- 3 つの fixture を `use std::data` 等の正しい区切りへ修正し(`a1699e48`、`d8cccf32`)、
  `parse_use_declaration` を `::` 受理へ修正した(`9f3f56e9`)。旧 `HeaderCursor` の
  `scan_plain_use` も同じ誤りで `TokenKind::Dot` を期待していたため、既存の
  `TokenKind::ColonColon` を見るよう 1 行修正した(`b8b97cc5`)。
- 続けて、CST 上で `::` が `SyntaxKind::Unknown` として出力されていた技術的負債を解消するため
  `SyntaxKind::ColonColon` を追加し(`4405bad6`)、`scan::punctuation` に `/` を追加し
  (`62abc7bd`)、`parse_use_declaration` が `::` / `/` どちらも区切りとして受理するよう拡張して
  realm 形式(`use realm/tools::format`)の regression test を追加した(`76961c23`)。
  フォーマット修正(`ad99fb69`)を含め全て push 済み。

### use 宣言の完全な文法・意味論設計

- 残っていた `mod` sugar・group import・alias・glob の実装可能性を調査したところ、現在の
  `UseDeclaration { range, path: Vec<WordSpan> }` という構造ではこれらを表現できず、先に
  Use AST・group 展開規則・mod sugar の責務分担を設計する必要があると判明した。yulang2-oracle の
  専用 use parser(504 行)と scanner(167 行)を精読し、Sol(xhigh)で use 宣言の完全な文法・
  意味論設計を `notes/design/2026-08-20-yu-syntax-chasa-architecture.md` に追記した(`f1e235a1`)。
- form 分類規則: `mod` は scanner 側で専用 contextual keyword、`realm` / `band` はどちらも
  専用 tag ではなく一般 `Ident` で、spelling 直後の区切り文字(`realm` + `/`、`band` + `::`)
  でのみ marker と判定する。`realm::x`、`band/x`、任意の `other/x` は全部 Plain のまま。
- Use AST は `UseTree` を中心にした再帰構造(`UseTerminal::Single/Group/Glob`、`UsePath`、
  `UseQualifiers`)とし、alias 反復・glob・`without`・operator segment・version / `with` anchor
  を表現できるようにした。version / anchor の意味論(manifest 連携、precedence 等)は
  future scope として構文だけ保持する。
- group 展開は depth-first で common prefix と form を継承し、完成した leaf だけを独立 record
  として commit する。`use mod` sugar の責務分担は、syntax 層が `form = Mod` と normalized path
  を保持するだけで synthetic module declaration は作らない、実際の module load 効果は
  source-loader 側の責任、と確定した。§18 の非 header `mod` / late `use` の source-set
  discovery とは別問題として切り分けた。
- version validation、`with` anchor 解決の precedence、schema revision の具体的 field shape、
  non-header `mod` の discovery mechanism の 4 点は Still open として明示的に残した。

### 7 スライス計画: grammar の公開 entrypoint 接続と旧実装の一括 cutover

- Use AST 完成を受け、「新 grammar を `scan_header` / `parse_file` へ実際に接続し、旧
  `HeaderCursor` / `lex` / `FullCstBuilder` を最後に一括削除する」という本丸の実装計画を Codex に
  立てさせた。7 スライス: (1) 公開 header fact と full-fixity table の一本化、(2) operator body 用
  opaque scanner の完成、(3) 新 header discovery driver(内部 candidate)、(4) direct Rowan
  full-parse session、(5) recovery/diagnostic 導入、(6) end-to-end ゲート固定、(7) 公開
  entrypoint の一括 cutover + 旧 path 削除。旧実装は新 pipeline が全 gate を満たすまで残すが、
  feature flag やランタイム fallback は作らず、public entrypoint を二系統にしない方針とした。
- スライス1着手前に、oracle の operator 宣言構文(`[visibility] [lazy] fixity (name)
  [binding-power...] = body`、fixity ごとに BP 個数が異なる、BP は dot 区切り vector、複数
  fixity は同 spelling への複数行宣言で与える)を調査で確定した。ユーザー判断: 同 fixity 再宣言は
  oracle のサイレント上書きではなくエラーのまま維持しつつメッセージを分かりやすくする、
  header fact の集約方式は実装しながら決めてよい。
- スライス1: `parse_operator_header` を 4 fixity・visibility(`pub`/`my`/`our`)・`lazy`・BP
  vector 対応に拡張し、`HeaderOperator` は一 source declaration を表す fact として維持したまま
  `OperatorTable::from_header_operators` で同 spelling の複数宣言を集約する設計にした。
  `ConflictingFixity` は spelling・fixity・両方の宣言 range を保持する形に改善した(`fe97fcba`)。
- スライス2(opaque body scanner完成、5 サブスライス): string interpolation `%{...}`
  (`6cc3e2c4`)、rule literal `~"..."`(`79af1e49`)、quoted/block Yumark `'[...]` / `'{...}`
  (`edc28dd6`)、Yumark code fence の raw/Yulang 区別(`69e68f99`)、known gap 記述の更新と
  横断 boundary contract のテスト固定(`cc0f2005`)。今回は珍しく Codex 自身が commit にまで
  成功する回が続いた。
- スライス3: use 宣言・operator header 宣言・opaque body scanner・group 展開を統合した新しい
  header discovery driver を内部 candidate(`grammar::header`)として実装した。旧 `scan_header`

  停止を検証した(`0eb4da0e`、`585cdc2b`、`62c99d55`、`669e678e`)。

### direct Rowan full-parse session の設計と実装着手

- スライス4に入る前に、「AST 構築ベースの現行 grammar から、どうやって `RowanSink` への direct
  emission を実現するか」という設計判断が必要と判明した。選択肢4つ(shared recognition core +
  commit-aware continuation / full 専用 direct grammar 新設 / AST 再走査で CST 復元(不採用、
  設計章の禁止事項に触れる) / 汎用 Emitter trait を常時渡す)を比較し、Sol(xhigh)で
  「shared recognition core + commit-aware continuation」を設計章の新章として確定した
  (`12a6f935`)。`Probe`/`Committed`/`CommitOutput` capability、NUD/LED の `probe_led`/
  `commit_led` 分離、typed `TriviaRun`、canonical `operator::OperatorTable` への一本化、
  `SyntaxKind` vocabulary 拡張を決定し、実装を6サブスライスに分割した。
- 実装1本目: `SyntaxKind` へ設計章の vocabulary 表にある全 variant を追加し、`scan_trivia` を
  text を所有しない typed `TriviaRun { range, parts }` へ発展させ(CRLF は単一 Newline part、
  未閉鎖 block comment は残 depth を保持)、`RowanSink` に `token_range()`/`emit_trivia()`と、
  node balance・token coverage・`green.to_string() == source` を検証する `finish_complete()`を
  追加した(`d4209df4`)。`grammar::declaration`/`expression`/`header` はまだこれらを使わない。
