## Phase 2: parser recovery と header discovery

### Compatibility fixture schema と fixture set

- Phase 0 の `tests/contracts/stable-core/v0/` は whole-compiler の run / check /
  public-signature snapshot 用であり、header / full parse の二相期待値、両者の parity、
  recovery node の `Missing` / `Error` 区別を表せないと分かった。Phase 2 向け fixture schema を
  `notes/design/2026-08-20-phase2-parser-fixture-schema.md` に定め、§4.2.2 / §18 との整合を
  確認した上で、ユーザー承認済みの正本として署名した。コミットは `421906be`。
- `tests/contracts/phase2-parser/v0/` に第一 slice を追加した。`leading-use-plain`、
  `infix-operator-header`、`malformed-header-followed-by-valid-header`、
  `header-full-diagnostic-identity` を含み、この段階では Yulang2 oracle anchor は置いていない。
  コミットは `1740306d`。
- 第二 slice では実際の `yulang2-oracle` grammar source と照合した `leading-use-mod`、
  `leading-use-realm`、`leading-use-band` を追加した。あわせて `late-use-after-body` で、最初の
  body item より後の `use` は `HeaderInfo` と full-parse header projection のいずれにも含めず、
  semantic dependency を結論しない §18 の境界を固定した。コミットは `90f316df`。
- 第三 slice では実際の `yulang2-oracle` CLI をビルド・実行し、
  `header-full-diagnostic-identity` の `full-missing-closing-paren` を oracle 出力へ anchor した。
  path-less `use` の候補 diagnostic は oracle で同じ形に再現しないため anchor しなかった。
  EOF `Missing` range は Yulang3 の `{26,26}` と Yulang2 の `{25,25}` で 1 byte 差があり、
  §4.2.2 が想定する presentation adapter による補正対象として記録した。コミットは `79310d15`。
- これで §4.2.2 の migration-order step 1、compatibility fixture set を完了した。

### 最初の実装と scanner の見直し

- `HeaderInfo`、`HeaderCoverage`、`HeaderImport`、`HeaderOperator` と `scan_header` の最小実装を
  `crates/yu-syntax/src/lib.rs` に追加し、`leading-use-plain` と `infix-operator-header` の fixture
  に対するテストを通した。コミットは `59ea69ef`。
- ただし line-oriented scanner は multi-line construct を持つ言語に適さないとユーザーから指摘が
  あった。`yulang2-oracle` の `lib/std/prelude.yu` に multi-line braced group `use` import、
  `lib/std/core/ops.yu` に nested control flow を含む multi-line operator body があることを確認した。
- `scan_header` を delimiter-depth stack と indentation を扱う token / trivia-aware `HeaderCursor` に
  差し替えた。公開型と対象 fixture の結果は維持し、group import と multi-line operator body は
  この slice の対象外とした。コミットは `e1737368`。

### 最小 full parse と chasa 必要性の確定

- Rowan は §4.2.1 / §4.2.2 の lossless Rowan bookkeeping と Yulang2 の `rowan 0.15` 採用により、
  既決の依存選択であることを確認した。`SyntaxEnvironment`、`ParsedFile`、`parse_file` を追加し、
  header discovery と full parse が同じ `HeaderCursor` lexer を共有することで header / full parity を
  構造的に保証した。対象 fixture に lossless `rowan::GreenNode` を生成できることを確認した。
  コミットは `7022ed27`。
- しかし dynamic infix `+!` と prefix `+` / `!` では、`a+!b` は `a +! b`、`+!a` は
  `+ (! a)` と読む必要がある。同じ文字列 `+!` の token 境界が parser position に依存するため、
  context-free maximal-munch の `scan_symbol_end` / `starts_distinct_item` は正しくないと分かった。
- `yulang2-oracle` が `chasa 0.5.0` と NUD/LED-dispatched operator scanner、
  `TrieState::longest_match_then` の checkpoint / rollback を実際に用いていることを確認した。
  chasa を用いる設計へ切り替える必要があると判断した。

### chasa-based parser architecture の提案と改訂

- `notes/design/2026-08-20-yu-syntax-chasa-architecture.md` の v1 では、flat token vec をやめ、
  direct chasa character-stream parsing、NUD/LED Pratt dispatch、event buffer を経た Rowan CST 構築を
  提案した。コミットは `8c5acd92`。
- v2 では、chasa は exact pin ではなく workspace crate として vendor し、rollback より
  `choice` / `or` を優先する実装規律を定めた。operator declaration は header-scoped のため、
  header discovery 後に immutable `OperatorTable` を一度だけ構築する。最初の slice から
  prefix / infix / suffix / nullfix を含む `BpVec` 相当の fixity を扱うこととした。
  また oracle の judge-table logic は変更せず採用し、event buffer / replay は廃して、speculative
  branch が CST を出力できない `Probe` / `CommittedCst` capability split を採用した。コミットは
  `93384066`。
- v3 では Yulang2 parser source tree と約 8,400 行の test suite を広く調査した。statement、lambda、
  `catch` / `operation, k ->`、pattern / type / rule、string / Yumark、role / impl / derives を含む
  grammar に対して core architecture が成立することを確認した。一方で `ParseLocal` の rollback
  ownership は input position だけでは不足し、`line_indent`、`inline` / `ml_arg`、Yumark の
  quote-depth / continuation など layout / scanner state 全体を戻す必要があると明確化した。
- header-mode の opaque body scanner も、delimiter depth と indentation だけでは heredoc、
  string interpolation、rule literal、Yumark 内の brace / newline を誤認するため不十分だった。
  lexical-region-aware scanner を要求し、これらを含む operator body の後に valid header が続く
  required-test-case family を追加した。コミットは `86f02267`。
