## 5. Why permitted transport does not repair the Int join

Theorem C §2.6 copies the complete old operand tuple and original scopes.
New coordinates are total derived definitions; they do not replace externally
fixed values such as `nu(b)` or `nu(d)` or introduce an unproved equality to
an endpoint. Its selected typed paths must already be present. Therefore
using the lift to manufacture an Int path from the Unit certificate is not
one of its allowed defining-coordinate extensions.

Typed-core §6 permits capture-avoiding renaming and **admissible endpoint
substitution**, preserving roles and entry skeletons. The nonempty example
has already fixed `a=c=Unit`; Unit is not a free type-variable name in that
ground instance. No substitution mapping that ground declaration/provider
and every original slot/consumer contract to the Int literal certificate is
specified or proved. The result/consumer coherence statement also expressly
does not establish invariance under unproved annotation conversion.

One may generate a *different* identity instance with a fresh parameter
endpoint assigned Int, as in the earlier note. That remains a separate
certificate-construction obligation for the Int literal/context; it is not
alpha-renaming of this existing Unit witness or a same-fiber containment
argument. No Unit-to-Int cast or adapter is presumed. The approved typed
observation projection retains value types and live `nu,K,D`, so erasing
concrete value identity cannot erase this mismatch either.

The source constructor shapes therefore establish the usable Unit case and
show exactly where direct Int reuse stops. No further Int profile or scope
transport is claimed after that first type-path incidence.
