its role-selected typed Function port and original profile, independently of
the pending Function comparison Q. The forward trace constructs only the
outer parameter role and source body/result skeleton from the supplied admitted
annotation premises. Complete-call construction preserves the received carrier
and its entry behavior, but does not supply the annotation-to-completed-port
association or the local original profile clause.

The exact unavailable output is a source certificate joining the original raw
occurrence/depth/scope to a typed position in the completed shared interface
and to the corresponding original profile clause with its predicate incidences.
The selected texts constrain this certificate and expressly leave its
constructor open. This is a bounded premise-extraction result, not a proof of
repository-wide absence, an accepted-source counterexample, or a new language
choice. Given that certificate and a separate original-profile activation

of this source contribution. It does not derive either source certificate.

This attempt adds a constructive trace at the static seam. It does not repeat

## Forward derivation and the precise stop

**1. Admitted outer parameter role.** Core §6 constructs Value(A) for an
ordinary value-annotated parameter, and Computation(E,A) for the explicit
outer computation forms. Annotated endpoints use the admitted annotation
derivation. This step fixes entry and the body environment; it explicitly
does not solve nested annotation checking or all receipt paths. A Function
stored in A can retain nested latent ports without changing the outer tag.
Therefore it provides no nested row-occurrence/profile relation by itself.

**2. Body/result skeleton.** Under that environment the core table constructs
the lambda skeleton `Value(Fun(P,Result(I_body)))`, with
`Result(Value(A))=Comp(empty,A)` and
`Result(Computation(E,A))=Comp(E,A)`. The names retain supplied symbolic
endpoints. Normalize's computation clause requires a *known corresponding
source port with its original profile*. Applying Normalize to construct the
missing profile would assume that very input.

**3. Complete invocation remains a separate construction.** Core §9 retains
the whole received carrier J_arg. For Value entry, the executing suffix is
entry Force, typed rebind, body and return, inside the actual complete view.
For retained entry, the carrier is bound without entry force and the body may
consume it explicitly. Thus J_body is the closure's Result(I_body), while
J_call is the complete ExecuteCallable image with its argument, environment,
configuration and designated result consumer. A pure identity body and a
request-bearing admitted argument carrier expose a request in J_call during
Force. A retained carrier and a constant body need not expose it at all.
These are the selected source reductions in §9, not new experiments.

This step prohibits identifying J_body with J_call or setting the complete
effect to an unconditional union. It does not determine which completed port
the raw annotation governs, or turn the surface arrow RHS into an already
solved complete-call profile. Any producer using a body skeleton must account
for the entry/carrier links before claiming that association.

**4. Polarization can follow a supplied typed position.** Choose the offered
receiver root positive. Its received callback formal has the reversed sign;
that callback's complete call port preserves the callback sign. Conditional
on a typed path `arg.callback.call.effect`, core §9 therefore derives its
negative sign. The receiver's own complete call effect is positive. The
calculation uses typed interactions, not omega or the family head; it cannot
choose omega's path or construct its clause. Shared epsilon references remain
views of the same scoped component at xi, not separate sign-indexed variables.
