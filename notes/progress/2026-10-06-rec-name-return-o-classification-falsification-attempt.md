## Two source-origin completions

Decorate source allocation judgments with `Ord(v)` or `Ex(v,l)`. `Ex` means
§22 introduced-existential classification at introduction level l; it is
additional source proof data. Neither decoration changes solver flexibility,
the graph binder partition, or the mathematical domain of assignments.

Both completions add the ordinary allocation clause

```text
ordinary collection creates v at level 1
----------------------------------------------------- Coll-Origin
the source allocation derivation records Ord(v)
```

This covers every collected row of this program, including c and r. They
also classify any earlier scheme instances in the retained history as
ordinary. The current incoming use has one fresh row z restoring the
constrained R bound. They differ on exactly this additional source clause:

```text
C_ord:
external pure member use creates the fresh constrained-R row z at level 1
----------------------------------------------------------------------- R-Origin-Ord
the use derivation records Ord(z)

C_ex:
external pure member use creates the fresh constrained-R row z at level 1
```

`C_ord` satisfies O. `C_ex` falsifies O at precisely z. The underlying
candidate endpoint/use judgment is identical after erasing these decorations.
Neither Name/Lambda generation nor the external graph freshening rule has
an origin premise that selects one decoration. Section 20 mandates request
opening but does not assert that request opening is the only possible
introduced-existential event. Its explicit distinction between request
binders and inference existentials supplies no R-origin classification.
Sections 22–23 constrain guarded comparisons once the classification is
known; they supply neither `R-Origin-Ord` nor `R-Origin-Ex`.

Four meanings remain separate: stored scheme category R; the fresh flexible
solver row z; mathematical `exists d` for a valuation witness; and the hidden
request binder opened to a rigid proof name. `C_ex` adds a classification
clause to z. It does not identify any of those meanings, infer Ex from the
word “exists”, or turn this source use into a request opening.

### Why collected c/r cannot be flipped while retaining an admitted prefix

The shared prefix contains the direct comparison `c <= r` at level one.
If either is classified Ex at introduction level one, §22's direct
variable comparison guard rejects that prefix against the other level-one
variable. Therefore merely declaring c or r existential cannot give two
common admitted allocation histories. The useful discriminator keeps their
classification fixed and changes the newly introduced R instance. This
constrains possible origin completions; it does not prove that every
collected row in a larger source is ordinary.

## Shared candidate coverage clause and exact outcomes

No added value task has two distinct variable endpoints. In particular,
q3's variable z occurs inside B, while c is the receiving variable. The
charter does not state which guard obligations this bound insertion creates.
Thus origin completions alone do not prove a guard-outcome discriminator.

For a precise relative countermodel, add the following **same candidate
coverage clause K to both completions**, restricted to this alias vocabulary.
Let V(t) be the set of variable identities syntactically occurring in t;
Top has empty support and neither Top nor P0 receives a level. At each
attempted value comparison s <: t, inspect every pair
`(a,b) in V(s) x V(t)`. If a is Ex(a,l), require `level(b) > l`; if b is
Ex(b,l), require `level(a) > l`. Failure rejects before commitment. Empty
support creates no pair obligation. In the absence of any Ex, this guard
component is vacuous. Guard inspection is not a generated subtype edge and
does not add a fifth value task to the audited trace.

K uses only variable levels, implements the selected equal/older rejection
on direct variable pairs, and is applied afresh to q4's replay. It is an
additional bound-dependency coverage assumption; neither ordinary structural
decomposition nor current production extrusion is claimed to derive it.
This restricted completion makes no claim about ground narrowing such as
`kappa <: Int`, operation arms, or general Function comparison. The selected
requirements for those omitted forms remain obligations, not new exceptions.

| Comparison | Variable support pair | C_ord + K | C_ex + K |
|---|---|---|---|
| q1 | (z,z) | accept | reject: 1 is not greater than 1 |
| q2 | none | accept | accept |
| q3 | (z,c) | accept | reject: level(c)=1 |
| q4 | (z,r) | accept | reject: level(r)=1 |

The C_ex execution stops at q1. Its q3/q4 entries describe the guard
judgment on those attempted shapes, not events occurring after rejection.
K supplies no reflexive-identity exemption. Such an exemption is not selected
by this note: if a later source rule suppresses the (z,z) obligation, the
distinct-variable q3 witness still separates the completions under the
remaining K coverage clause. Hence failure does not rest solely on a
self-comparison convention.

The smallest distinct-variable witness is q3, the structural bound B(z)
against c, with only z classified Ex(1). Two distinct level-one variables
are required for this witness; Top and the two P0 heads encode the actual
scheme bound. Removing the alias removes this caller witness; removing q4
does not remove it. Reclassifying z ordinary makes every guard in this
four-shape trace vacuous. Changing c to a younger variable would permit q3
under K but violates the audited all-one inventory and direct-neighbor level
invariant. Removing K leaves the structural coverage question open; it does
not establish either guard result from the selected rules.

## Exact consistency scope and blocker

The models preserve the candidate pure graph judgments and graph denotation
after origin erasure, the stated freshening/ownership requirements, absence
of a §20 request introduction in this source, and §22 direct variable
rejection with §23 variable-only levels. Their conditional guard results
use K on every attempted initial/replayed shape. This is relative consistency
of a restricted origin/guard interface; it is not a proof of a complete
Yulang source calculus or a complete extension satisfying all request,
ground-type, extrusion, source-adequacy and lifecycle obligations.

In particular the candidate graph's defined acceptance relation is not
silently replaced with graph satisfaction plus this guard. That conjunction
would be a new source-admissibility definition and could shrink that
candidate relation. The actual A_alloc/A_final are still missing. The
countermodel refutes inference of O from the named origin-free judgments;
it does not refute the reviewed conditional theorem assuming O, or law `(L)`
for an eventual source-derived A.

Precise blocker to the stronger requested discriminator: a source rule must
first classify the fresh constrained R instance, and a guard rule must then
say whether its occurrence inside a structural lower bound generates a
permission obligation against the receiving equal-level row. Four-pair
production closure and all-one level invariance supply neither rule. A
checker that takes the above labels/K as input would only verify this
conditional table. A larger model or another equivalent toy probe would
leave both source premises untouched.

Recommended next action: obtain the source allocation/member-use origin
clause together with its structural-bound guard coverage; apply it to q3
before widening the target inventory or attempting full `(L)`.
