# X22: optional input rejected by the main pattern generator

Status: confirmed mismatch with the decided rule, not a request to change the specification.

```yulang
-- The input type has an optional port field.
case input:
    {port: p} -> p
    _ -> 0
```

`spec/03b-patterns.md` §3b.3 permits this pattern. If `port` is absent,
the first arm misses and evaluation continues to the next arm.

The existing `CommonOptionalFieldBoundary.subject` is the concrete type
`exactEmpty | required port int`, and its `pattern` is `{port: p}`.
`CommonOptionalFieldBoundary.strict_rejects` proves that the main
`CommonAlignedPatternTyping.RawTyping` judgment rejects that pattern for
every environment and every output binding list. The corresponding
`CommonAlignedPatternGeneration.generatePattern` is exact for that judgment
and emits a required-field constraint. The actual matcher does miss for an
empty record. A separate `CommonOptionalField` judgment and generator already
accept this input, but they are not integrated into the main generator.

Repair options:

1. **Recommended:** integrate the existing optional-field rule and its
   generator into the full source pattern judgment, retaining the actual
   matcher's miss path and proving the combined generation and case results.
2. Rebuild the field rule around a refined success-branch input and separately
   prove its equivalence to the existing optional-payload rule and matcher.
3. Split presence analysis into a source validation pass and a subsequent
   success-branch elaboration, proving their composition equivalent to the
   decided rule.

These are implementation choices; none changes the owner's decision.
