# I-60: record の下端・上端を読めても、実中心の由来だけが未完了の場合

## 案 1（遅延・現証人境界のまま）

下端と上端の支持があれば候補照合はできる。実中心の record 捕捉を正当化する supported read または承認済みの区間射影がなければ、候補を確定・発行しないで保留する。未完了出力の等式自体は通常状態に保持する。根 K2 はこの例にはなく、I-58 の共有変数の等式欠落で保留にした例でもない。

## 案 2（別の、支持だけを使う record 射影が承認される場合）

両端の実支持、区間と record の構造が独立に十分なら、未完了側の RHS を使わずに実中心の可視 field・残余を通常の構造射影で再構成する。それができる場合だけ進める。等式が真というだけで支持へ昇格する案や、旧 Local に合わせて普通行を読む案ではない。どの record 射影が承認済みか、特に open/closed の残余の扱いを確かめたい。

## Yulang での状況（模式例）

```yulang
role Hold 'u:
    type witness
role W 'u:
    type out
role Pick 't:
    type out

impl W (list 'u):
    where 'u: Hold
    type out = {x: int}

impl Pick {x: 'a, ..'rest}:
    type out = 'a
```

需要は `(list 'u): W(out = 'center)` と `'center: Pick(out = 'result)`。W の where は `list 'u` から `'u` に降りる。別のソース制約から `'lo <= 'center <= 'hi`、両端の record 頭は分かるが、実中心の record 行の由来は未解決の `Hold` を持つ W の出力のみ、という状態を考える。上の断片そのものを Rust 実行してこの状態に到達したとの主張ではない。

## Lean で確認済みの切れ目

`GeneralDeclarativeWitnessCut334`。checked な実 record impl、支持された両端、有効な通常モデル、I-59 の非循環、実コンパイラによる固定出力 `5=3`、同じ ordinary receipt を持つ。旧 `Local59 / Staged` は selected。現証人分類では、実中心名 1 に届く支持された alias が他名にならず、名 1 の RHS の由来は未完了 owner 100 のみ。named・inline・現行 projected のどれでも中心を読めないことを証明し、pending、selected 辞書なしを確認した。旧 solver が実際にこの状態を返すこと、または言語全体の不一致は未証明。案 2 は未証明・未実装。

### 再確認：遅延解除の最小条件

同じ fixture で、区間・普通の等式・モデル・由来表は一切変えず、完了の述語だけを任意に変えた。Lean の `exactly_completed` / `pending_iff_incomplete` により、新分類が同じ宣言を同じ子列で選ぶのは owner 100 が完了したときに限り、それまでは保留になる。100 と無関係な完了では変わらない。完了後は、すでにあった中心の record 行を読み直し、同じ固定出力先でコンパイラを通し、実モデルで辞書の証拠まで得る。solver が実際に owner 100 を完了へ進めることはこの結果からは言えない。

## 回答（2026-11-22、ユーザー）

**案 2 を採る**（ユーザーの決定「2」）。中心の行は使わず、根拠のある下端・上端から照合し、捕捉を区間として作って選ぶ。W が片付くのは待たない。spec 6.5「実際の引数の名前（中心）は明示して持つ」の下に記録し、B4 草稿の補遺 10 に入れた。理由（監督役の推奨に同意）: 同じ節の既決の規則が「解決は端点で行い、中心は型変数の使い回しを表すためだけに使う。共有の情報を失ったことを理由に保留にする規則は足さない」と言っていること。この例の `'a` と `'rest` は一度しか現れないので共有は要らない。
