# C378: the ordinary crossing root is cheap; native entry is not

I-65 step 1. The following is an exact source-level distinction in
C321 `Visit`, not a new language rule or a claim about an actual full
native scanner. The execution provider was initially offline.

## Any ordinary walk starts with an inspecting expression

Fix any ordinary view `V`, logical name `n`, and translated source
query `e`. There is a `Visit V n e site` for some ordinary site iff
`Inspects e`. More precisely, any ordinary walk entails
`Inspects e`: inspect its first constructor. The `here` constructor
has that witness already; the primitive, nominal, field and variant
constructors have the corresponding inspecting outer expression.
Conversely `Visit.here` gives `Visit V n e n`. It requires no
`V n …` shape fact, no fitted model and no successful deeper
comparison. Thus existence of some such walk is independent of
ordinary support, although **which descendants** are reachable is
not. A variable query has no visit, in agreement with C321's existing
negative lemma. A join also has no direct constructor in this ordinary
view; that is a proof-domain boundary, not a language verdict.

On an *independently entered* native-to-ordinary crossing, this
observation has a positive application: if the exact original
effective-port payload is literally `.ordinary (.var n)`, and the
actual authored subpattern translates to an inspecting `e`, the
first **ordinary** visit at `n` is `.here`. There is no need to
produce a supported ordinary interior head merely to construct
that first ordinary visit. Check K2 at that site on the unfiltered
ordinary graph, e.g. via C374's local-return equivalence. A pending
ordinary row may cause K2 there even if it cannot support descent.
Taking another ordinary step, by contrast, really requires the
particular supported shape in the relevant `Visit` constructor.

## Why C369's proposed record cannot alone authenticate early entry

The private `NativeOrdinaryInspection` draft starts from a C377
possible endpoint port, a separately lower-backed original, a
literal payload/name, normalized source query, same-state support
and normal lineage, and a positive ordinary `Visit`. For an
inspecting query, its `site := logical` and `visited := .here …`
fields can already be constructed from those data. Neither field
cites a native step, a visited native parent, nor ordered dispatch of
this exact child ordinal/job face. Therefore the record is usable
as a conditional ordinary continuation *after* native entry, but
cannot serve as proof that the candidate actually entered. Requiring
`Visit` instead of a possible port is essential for deeper ordinary
descendants, insufficient for independently establishing the very
first crossing.

The missing constructor/proof must link a positively visited native
parent to entry of this literal original child under the approved
source traversal; it must carry the same request occurrence, visible
candidate, inherited mode and positions. Use the actual supported
lower readiness gate and keep original physical release and
source-specific context separate. An upper-only physical origin is
not that entry. Root K2 from the unfiltered equations remains the
earlier independent test, even when no candidate may newly expand.
No new acceptance, pending or veto policy is proposed. Do not use
this equivalence to test all potential jobs or pretend an entire
native visit trace is available. No fixture was added.
