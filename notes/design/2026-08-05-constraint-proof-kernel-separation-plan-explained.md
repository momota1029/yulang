## 1. 今日、実際に何が起きたか

抽象的な話から入る前に、今日一日で実際に踏んだ事故を並べる。全部同じ
根っこから生えてる。

### 事故1: RCPF-Eの「完了」が実は完了してなかった

RCPF-E（証明の読み取り経路を新しい表現へ切り替える作業）を、§11という
文書に書かれた4項目に沿って完了させて、正本文書に「着地済み」と書いた。

ところがRCPF-F（古い表現を物理的に消す作業）に進もうとしたら、
「§11には書かれてないけど、古い表現を無条件に読んでる場所」が
**5箇所**も見つかった。§11の4項目を全部確認したはずなのに、確認の
対象自体が狭すぎた。

### 事故2: 承認済みの設計文書に、実は矛盾があった

その5箇所のうち1つを直そうとしたら、「これは以前ちゃんと設計を詰めて、
ユーザー承認まで得た規則のはずなのに、実際のコードの挙動とも、既存の
テストが固定してる挙動とも食い違ってる」ということが判明した。

つまり、**承認までしたはずの設計文書自体に見落としがあった**。

### 事故3〜4（今週の履歴から）

これは今日だけの話じゃない。DPN、URR-v3という過去の追補文書も、
「一見大丈夫そうに見えて、実は特定の状況で証明が壊れる」という同じ
パターンの発見・修正の繰り返しだった。

### 共通点

4つとも、「型推論そのもの（この型はこの型のサブタイプか、みたいな
本質的な判断）」が間違ってたわけじゃない。間違ってたのは全部、
**「なぜその判断が正しいと言えるか、その証拠をどう記録・追跡するか」**
という部分だった。

そして、この証拠追跡の部分は、型推論の本体コードとがっちり同じ場所に
混ざって書かれてる。だから証拠追跡の都合で何かを変えようとすると、
型推論の本体まで壊れないか毎回慎重に確認しないといけない。今日
これで何時間も溶かした。

## 2. 「意味論」と「証明」を分ける、ってどういうことか

一番わかりやすい喩えは、**裁判所の「判決」と「証拠書類」の分離**だと思う。

- **判決**（＝この設計文書でいう「意味論」）: この型はこの型に代入できるか、
  できないか。この変数はこう束縛される。この関数はこの型を持つ。
  ——最終的にユーザーに見える「型推論の結果」そのもの。

- **証拠書類**（＝「証明」）: なぜその判決に至ったか。どの制約から
  導かれたか。どの箇所の記述が原因か。同じ結論に複数の経路から
  たどり着いた場合、それぞれの経路を後から説明できるか。
  ——エラーメッセージの「なぜ」、コンパイルキャッシュの正しさ、
  ジェネリクスの汎化、といった「判決そのものではないが判決を支える
  仕組み」。

今のYulangのコードは、**判決を書く部屋と証拠書類を整理する部屋が
同じ部屋**になってる。1つの型制約を処理するたびに、「この制約は
成立するか」を判定する作業と、「この判定の証拠をどう記録するか」
という作業が、同じ関数の中で同時に行われてる。

これを2つの部屋に分けよう、というのが今回の計画の核心。判決を書く
部屋（core solver）は今のまま残す。証拠書類を整理する部屋
（proof kernel）だけを、もっとまともな棚に作り直す。

### なぜ「棚が悪い」と、今日みたいな事故が起きるのか

今の証拠書類の棚は、実は**2組**ある。昔からある「紙の台帳」
（flat representation）と、後から作った「速い索引」
（factored representation）。索引は台帳の中身をもとに作られてて、
本来なら「索引だけ見れば十分」なはずなんだけど、まだ台帳の方も
律儀に更新し続けてる（そうしないと、索引に何か問題があった時に
台帳へ逃げられないから）。

これが**事故4**（性能profileで見つかった「74%が二重記帳のコスト」）
の正体。RCPFという一連の工事は、この二重記帳を段階的に「索引だけで
足りる」状態に持っていって、最後に台帳を捨てる、という計画だった。

でも、今日露呈したのは、**台帳から索引へ移すだけでも、想定より多くの
場所で「実は台帳の方だけが持ってる情報」に依存してた**という話。
これが事故1（5箇所の見落とし）と事故2（規則自体の矛盾）。

## 3. なぜ「証拠書類の部屋」を完全に切り離せないのか

理想を言えば、証拠書類の部屋は判決の部屋から完全に独立させて、
「判決が出た後に、後追いで証拠を整理するだけ」にしたい。実際、
Solに調べてもらったら、型推論の本体アルゴリズム（worklist処理、
サブタイプ判定の分解規則、行多相の簡約、SCC、汎化）は、**証拠の
中身を一切参照せずに動いてる**ことが確認できた。だからここは
本当に変更不要。

ただし、**4箇所だけ**、判決を出す途中で証拠書類を覗きに行く箇所が
見つかった。

1. **リプレイの実行判断**: 「この制約が新しく成立した時、過去の
   別の制約と組み合わせて再チェックする必要があるか」を、証拠側の
   カバレッジ情報を見て決めてる。これは「証拠を記録する」んじゃなくて
   「これから何を計算するか」を左右するので、後回しにできない。

2. **汎化できるかどうかの判定**: 変数がどこまで具体的な型として
   外に見えるべきか（＝ユーザーに見える型そのもの）は、証拠側の
   「この束縛はどこから来たか」の論理式（AND/OR）を評価して決まる。
   これも判決そのものに直結してる。

3. **証拠が壊れた時の打ち切り**: 証拠の記録に失敗したら、その
   コンパイル試行全体を「なかったこと」にして、安全な旧方式で
   やり直す。この「丸ごと打ち切る」判断も、証拠の状態を見ないと
   できない。

4. **再計算のトリガー**: ある型が「汎化できる/できない」の判定が
   後から変わった時、それに依存してた他の計算を再実行する必要がある。
   この通知も証拠側から判決側への連絡が要る。

だから、正確には「証拠書類の部屋を完全に無関係にする」んじゃなくて、
「判決の部屋が証拠の部屋に問い合わせる窓口を、この2つ（実行判断と
汎化判定）だけに絞る」というのが実際の設計。それ以外の経路
（診断メッセージ、キャッシュのための証明書き出しなど）は、本当に
後追いだけで済む。

## 4. 具体例で追ってみる

「`a <: b` という制約が新しく1つ処理される」場面を、今の設計と
新しい設計で比較する。

### 今の設計

```
1. a <: b を受け取る
2. サブタイプの分解規則を適用（判決の仕事）
3. 分解でできた子制約をキューに積む
   ↑ この時、同時に「この子制約はどの親から来たか」を証拠帳へ書く
4. 証拠帳への書き込みで、台帳（旧表現）と索引（新表現）の
   両方を更新する
   ↑ ここで、5.のような見落としが起きうる
5. 証拠の一部（claim-parent）を使って、汎化できるかの判定も
   同じタイミングで更新する
```

3〜5が全部同じ関数の中に混ざってるから、「3だけ直したつもり」が
4や5を壊す、というのが今日起きたこと。

### 新しい設計

```
1. a <: b を受け取る
2. サブタイプの分解規則を適用（判決の仕事、変更なし）
3. 分解でできた子制約をキューに積む（変更なし）
4. 「こういう子制約ができました」というイベントを1つ、
   証拠の部屋へ渡す（渡すだけで、判決側はもう関与しない）
5. 証拠の部屋が、そのイベントを自分の棚（1種類だけ）に記録する
6. もし今回、汎化判定に関わる変化があれば、証拠の部屋から
   「この型変数、再計算が必要」という通知だけが判決側へ返る
```

判決側のコードは3までしか触らない。証拠の記録方法をどれだけ
変えても、判決側は「イベントを1つ投げる」というインターフェースしか
知らなくていい。

## 5. なぜこんなに段階（CPK-0〜CPK-9、10段階）が必要なのか

一気に切り替えたら早いんじゃないか、と思うかもしれない。実際、
今日「バッサリいってみる」を試して、RCPF-Fで一部それをやった
（branchを切って直接消してみた）。結果、消す前に本物の見落としを
2つ見つけられた——事故として損害は出なかったけど、これは
「実際に手を動かして初めて見えるギャップがある」という実例でもある。

段階を分ける理由は、この見落としを**production（実際にユーザーが
使う経路）に影響が出る前に**見つけるため。大まかな流れ:

- **CPK-0**: まず「今何が起きてるか」の棚卸し。今日見つかった
  未解決の矛盾（事故2、事故1）もここで先に片付ける。
- **CPK-1〜4**: 新しい証拠の部屋を作るけど、**まだ判決側は
  古い部屋しか見ない**。新しい部屋は横で「答え合わせ」だけしてる
  状態（shadow）。ここで新しい部屋の設計ミスを、実害ゼロで
  見つけられる。
- **CPK-5〜7**: 答え合わせで問題なければ、判決側の参照先を
  新しい部屋へ実際に切り替える。ここが一番危険なので、
  「実行判断の切り替え」と「汎化判定の切り替え」を別々の
  タイミングでやる。
- **CPK-8**: 古い部屋（台帳と索引の二重管理）を物理的に撤去。
  ここでようやく事故4（74%コスト）の大部分が消える見込み。
- **CPK-9**: 最終確認と性能計測。

「急がば回れ」というより、「今日みたいな見落としを、ユーザーの
コードが壊れる前に見つけるための保険」だと思ってねぇ。

## 6. 終わったら何が変わるか

- エラーメッセージの「なぜ」や、コンパイルキャッシュの正しさを
  支えてる仕組みが、1つの分かりやすい表現に統一される。
- 型推論の速度そのもの（`std::text::parse`のような重いモジュールの
  コンパイル時間）が、二重記帳のコストから解放されて改善する
  見込み——ただし本編にも書いた通り、これは「やってみないと
  正確には分からない」ので、CPK-9で正直に計測する。
- 今回のような「承認したはずの設計文書に矛盾が見つかる」事故が
  起きにくくなる。1つの表現しかないので、比較対象がそもそも
  存在しなくなるから。
