# I-56: ordinary equations to the actual head and shared capture

C319's ordinary atoms do not have an invariant-nominal term constructor. A
conservative extension by **ordinary logical equations** can say that one
logical variable is a compound type expression in other logical variables.
It stores neither declaration choices nor dictionaries. The empty extension
must have exactly the old models. A pure equation is not a test that one
candidate can survive: selection still needs a separate declarative rule.

Actual local target, for any ordinary-extension state and every model:
if a source pattern compiles and a finite syntax-directed derivation reads
the center via constructor equations, sharing the variable centers recorded
by ordinary mutual bounds, then the center is equivalent to the normalized
source head under that same capture. Repeated head variables must use a
single logical capture, not arbitrary potentially unrelated members of the
same interval. Nominal children use actual values; structural constructor
equations are interpreted in the full carrier. Next combine this head result
with where bounds and outputs, keeping order and provenance.

This is a sufficient local certificate over the model theory, not a new
criterion of acceptance. Whether the accepted declarative Classify always
provides the certificate is a separate obligation. In particular, neither
a potentially satisfiable candidate nor merely matching interval endpoints
is assumed to justify evidence in every model. Do not insert a new guard
into Classify just to make a proof hold.

## Finite compiler and the real cut

The separate pure compiler emits finite logical equations from a source
declaration, its ordered children and its logical names. Nominal arguments
use actual-mode names even inside a lower/upper expression. A checked role
default reads positional centers, not impl-capture identifiers. An equation
need not be textually present if it follows from ordinary constraints. Adding
only such equations or derived capture bounds leaves the set of models equal.

The two checked `wrap` examples separate the local-versus-completed boundary:
the real parent uses a nominal head whose actual center has no stored equation,
requests `item` from a genuine child, and uses that named result in its own
compound output. If only the child's `item = actual-arg` equation is removed,
all parent equations are still entailed and there is still a normal model,
but the child dictionary fails in that model. This is not a claim about an
approved rejection case. The type rule must not confuse candidate survival,
or even parent local materialization, with a completed successful dictionary.

After C320 the cut is `selected local front -> ChosenRecipe or BatchRecipe`
with genuine source capture/where/out constraints. In particular a successful
result cannot use only endpoint overlap or one feasible matching model to
justify a repeated actual binder. The approved delayed handling of unresolved
dependent outputs and the promise not to add a refusal merely because an
implementation lost a center identity both remain untouched.

## Repeated binder hand-off

For a variable-only head, no new semantic substitution is supplied by hand.
The logical declaration/argument table chooses the first actual occurrence as
a representative. Mutual ordinary inequalities link each occurrence to that
one center. The join/meet equations supply the exact combined bounds, and a
conservative ordinary closure makes them available to the downstream
where/output compiler. Different occurrence orders induce equivalent captures
in all three modes when both merge facts are valid, but this is not an
order-independence theorem for resolver decisions.

Next work should build the *independent accepted local frontier*, not add
a readiness test to make the proof automatic. Separate these obligations:
1. The logical lower-head/K2/readiness derivations, preserving the approved
   delayed treatment of only-unfinished-output support. Ordinary output
   equations may still constrain all models; don't equate semantic entailment
   with a license to unfold a pending child.
2. From the surviving declared head, produce actual capture-origin facts
   and the ordered logical names of child demands. Invariant nominal or
   mode-insensitive branches need no explicit center equation; open
   covariant branches still need genuine actual projections.
3. For each selected local branch, show ordinary entailment of the concrete
   compiler's generated head/where/named-result equations, or the corresponding
   direct read recipe. A satisfiable candidate is not this assertion, and a
   materialized parent is not a completed dictionary.

All three are facets of the one source-side `Compiles` cut remaining in (4).
Neither a theorem of rejection nor a solver-state projection has been stated.
