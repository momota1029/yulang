# C303: 再索引された refresh と install 列

## 今回 Lean で確認できたこと

- 更新前後でソース側から見える install のデータが一致すると、予約 ID・割当キー・通常の制約原子が一致する。各 install でこの条件を満たす二つの有限列について、スロット対応、ソース変数の被覆、信頼済みキャッシュ・制約を含む refresh 証明書を列全体にわたって移せる。ID の通し番号が両側で同じである必要はない。
- install のプランが既存の全モデルで成立し、install 前後に出力要求がなく、旧経路の副作用も空なら、install 前後のモデル述語は同値。この条件の下で、対応する二つの install 後もモデルの一致を保てる。
- 各ソース ID のモデルが有限の nominal tower なら、すべての ID に共通の深さ上限を置かなくても、raw K2 の辺では深さが真に減少し、閉路がない。pair・record・variant・空の構造先頭と tower の先頭は区別できる。未使用の空 record 形状をカタログに追加した具体例でも、既知性・相互 refinement・記録された観測結果の同値を確認した。

## 検証と範囲

新規 Lean 12 モジュールに対する対象限定の `lake build --wfail` と、独立した `Audit/Cycle303*.lean` に対する `lake env lean --trust=0` が成功（33 宣言。依存公理は Lean 標準公理のみ、またはなし）。[監査ログ](../verification/cycle303/) と [設計ノート](../design/2026-11-20-cycle303-ladder-phases.md) を同梱した。差分検査 `tools/verify-lean.sh … --no-build` も通過した（別途の静的検査）。公開したコード・監査・ログの計33ファイルの Git blob ID を、ローカル検証済み版と GitHub から再取得した版とで照合した。全体ビルド、Rust 実行、CI はしていない。I-54 が引き続き最新。統合ブランチや仕様・Rust は変更していない。

上の有限列の定理は、各段の install が対応することを仮定する。任意の早期 refresh 後にその install が実際に選べること、選択が一意であること、混合した raw 遷移全体の停止性は未証明。次は既存の証明書を使い、実際の raw `Step` の最初の install の存在と分類を確認する。その後、履歴の plan/effect が異なっても対応を維持し、停止時の辞書とステップ数を比較する。下書きは作業環境に残したが、深い既存の依存グラフの冷間再ビルドが枠内に完了しなかったため、今回の公開には含めていない。
