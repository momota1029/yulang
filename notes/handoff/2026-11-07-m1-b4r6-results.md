## 1. 証明した主要statementの全量化

`Yulang.CommonRoleStablePaterson.check_sound`:

**任意有限Declaration D**、**check D=true**、**任意child∈D.requirements**、
**任意σ:Nat→Form**について、

```text
argsSize (N(child[σ])) < argsSize (N(D.head[σ]))
かつ、任意name:Natについて、
argsOccurrences name (N(child[σ])) ≤ argsOccurrences name (N(D.head[σ]))。
```

Formは有限var/int/pair/union/tick構文。Nはrecursiveな同一union branch縮約stage。
実Term encode、実Roles.size_decreases、有限occurrence計算に接続する。
成功する実instance、resolverの停止、fuelを追加前提としていない。
Boolcheckは有限comparison Roles.Implを作って実CheckedRoles.checkImplを呼ぶのでdecidable。
semanticな全称条件そのものを入力証明にしていない。
**任意Common/regular代入についての完成した全言語checker定理とは呼ばない。**

`Yulang.CommonRoleStablePaterson.accepted_wellFormed`:
**任意Declaration D**について、**check D=trueなら**、実stored **D.toImpl.WellFormed**。

`Yulang.CommonRoleStableRecordResidual.checked_residual_decreases`:
**任意payload型、任意明示label列labels、任意有限具体row goal**について、
**有限宣言check labels=true** かつ **実lookupのheadMatches labels goal=true**なら、
**任意payload size weight:Payload→Nat** と **任意occurrences:Nat→Payload→Nat** について、
実canonical capture labels goalのnormalized sizeは元goalのnormalized sizeより真に小さく、
**任意name**でnormalized captureのoccurrence countはnormalized goal以下。
label checkはpayload型照合全体の代用ではなく、このrecord tail branchに必要な実計算のcomponent。
canonical residual以外のtail代入を存在仮定で渡していない。

## 2. checker の設計と範囲

headの安定rigid位置だけをlowerに数える。merge下はsize1/occ0として保守的に扱う。
childはsymbolic N後の全構文をupperに数える。
comparisonの通常Paterson条件により、任意N済代入像でupper child<lower head。
両側の実N後値を挟むので、後から新しい合流が生じても真下降とocc非増加が保存される。

unary descent、pair再構築、同一payload重複をNしてからの下降、merged headから小さい定数child、任意terminal headを受理する。
第五回の9/5→5/5例は宣言check=false。新しい利用時size拒否は導入しない。
proper-subterm限定より広い一方、全称semantic条件の完全なcheckerだとは主張しない。
全record/variant/arrow/effect/nominal/source normalizationへの統合は残る。
代案と理由は [設計note](../design/2026-11-07-b4r6-stable-envelopes-and-capture.md)。

## 3. 一つの必要なユーザー判断

```yulang
role R 't:
    type value

impl R (:{tick 'a, tick 'b}):
    type value = int

impl R (:{tick int}):
    type value = int
```

確定goal `R :{tick int}` に対し、最初のimplの合流前変数a,bの操作的な捕捉が未指定。
whereなしなので新Paterson条件は空に成立し、定数associated RHSはHDAを満たす。
両方へintをそのまま捕捉するなら二候補で曖昧。
合流前の変数が一意に決まるまで待つなら、未確定candidateを残して解決全体の保留が必要になる。

[一問](../questions/2026-11-07-b4r6-merged-head-capture.md) に推奨を先に記した。
推奨は、plain variable branchの両方へ合流済みpayloadを捕捉し、この例は曖昧とする選択肢1。
この判断をspecから導いたことにせず、任意Common completion存在を独立head semanticsへ勝手に置かない。
原契約addendum「書かれていなければ、E2を出す前にnotes/questions/へ1問」に従った境界。
第一terminal implの一律拒否で問題を隠したfull E1も出していない。

`CommonRoleMergedCaptureBoundary` は、二実declのstable check/WF、定数associatedの実HDA、実head解釈を証明する。
固定数学的completion (int,int) と (never,int) が同じhead意味を与えるが変数0像は非同値であることを示す。
**いずれかを実solverのcaptureとして採用した定理ではなく、E2でもない。**
