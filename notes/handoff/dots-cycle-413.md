## 今回入れた規則と検査

- C05 は、実際に宣言された入れ子のレコード候補を一つと、実際にマッチする束縛だけのレコード候補を一つ以上含む範囲です。元の引数は一つの point、外側の行は `box` 一フィールドで、候補に書かれたレコード末尾・where・出力は空です。元の可視候補リスト全体を宣言 ID と出現順のまま読み、宣言にない候補や順位を足せません。
- `Check {box:'a}` は `box` の値を束縛して止まります。`Check {box:{next:'b}}` は同じ値のレコード構造を実際に検査します。X11 の `μ={next:μ}` は後者が訪ねるフィールド位置 1 で K2 です。親の位置 0 は非循環で、位置 1 の raw alias でもありません。フィールド到達と元の未フィルタのグラフ上の閉路を別々に反映し、親 K2 や where の要求として代用していません。
- 既存の R4 にこの拒否規則だけを加えた R5 に対して `DictionarySound` を証明しました。実行検査器は有限な元入力と証明書のデータだけを受け取り、既存の `Check408.Result` をそのまま使います。`MixedRecord413.check_sound` は同じ State と適合するすべてのモデルについて従来の契約を保ち、元の検査器の判定および既存の選択木・順序付き固定書込みと有限な支持を変更しません。`locate` は別口で、実際の候補列、出現、経路、フィールド位置を返します。
- 実際の二候補を両順序で、実際の束縛候補をもう一つ加えた入力を全六順列で検査しました。いずれも元の候補列を保持し、同じ宣言 57・位置 1 に対応する元の序数が正しく変わります。同一の元入力では別の証明書でも位置・序数を付け替えられないことと、実際の行読取りを保つ順列についての判定不変性も証明しました。
- 対照実験は、束縛候補のみ、入れ子候補のみ、未対応の第三候補、非循環、従来の親 K2 を含みます。別の適合モデルを持つ非循環入力では両候補が独立に実際の head にマッチし、候補列を読み切れますが、新しい K2 分岐はどの証明書でも false です（実行結果 `[true, false]`）。この false は言語自体の拒否や曖昧性の判定を主張しません。
