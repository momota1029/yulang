# Yulangドキュメント文章リズム規範

本規範は、Yulangドキュメントサイトの日本語と英語の本文、および両言語の翻訳対に適用する。
日本語の表記、文法、段落、コード例に関する基礎規範は、[Yulang日本語文章作法](./japanese-writing-guide.md)とする。
本規範はその上に、読者の読み方に応じたリズム、英語に固有の選択、翻訳対の同期方法を加える。
基礎規範が同じ範囲を同じかそれ以上の具体性で扱う規則は、ここでは繰り返さない。

正確さ、前提の充足、検索可能性は、読み味より優先する。
リズムは情報を隠す演出ではなく、読者が観察、判断、確認を切り替えるための構造である。

## 適用する三つの層

ページのディレクトリではなく、そのページで読者が何をしているかによって層を決める。

- **通読層**：読者が先頭から順に読み、操作や推論を積み上げて学ぶページ
- **参照層**：読者が必要な事実、手順、構文、APIを途中から引くページ
- **規則層**：読者が推奨、禁止、落とし穴を引き、書き方を選ぶページ

一つのページに複数の性格があっても、表に定めた主たる層をページ全体の既定とする。
節が明らかに別の読み方を要求する場合だけ、その節に別層の規則を局所適用してよい。
たとえば「参照層」の長い worked example は「通読層」の拍を使えるが、前後の項目の自己完結性は崩さない。

## 要ユーザー承認の日本語文体

**判断点**：日本語の「通読層」は敬体、「参照層」と「規則層」は常体で書く。
この分け方は、ガイド系ページの敬体とリファレンス系ページの常体という公開サイトの声を保ち、読者の行為に文体を合わせるための判断である。
これは基礎規範の「本文は常体」という規則に対する、サイト本文だけの狭い例外になる。
ユーザーがこの判断に署名するまでは例外を発効せず、基礎規範どおり全層を常体で扱う。
引用、UI文言、診断文、コード内の文字列は、どちらの場合も本文の文体判定から除く。

## 層ごとのリズム

### 文の拍

「通読層」では、短い文で観察対象を置き、条件や経過を少し長い文で運び、短い文で到達点を固定する。
この並びを全段落へ機械的に当てはめず、操作、診断、期待外れの挙動といった転回点に使う。
短文を三つ以上並べると、すべてが強調に見える。
一つを残し、残りは因果か時間の関係が見える文へ戻す。

「参照層」では、文長の劇的な変化より、情報の定位置を優先する。
概要、構文、条件、結果、失敗、例が同じ順で現れるなら、拍はその枠内で作る。
複数の条件を運ぶ文の直後に、結果を短く置く程度で足りる。

「規則層」では、短い規則、理由を運ぶ文、具体的な違反例か修正例の順を基本とする。
禁止だけを短文で重ねず、何が壊れるかを同じ項目で示す。

どの層でも、拍を作るために前提、例外、失敗条件を削らない。
長さを変える材料が対象側にない箇所は、平坦なままでよい。

### 段落の密度

「通読層」で密な説明が二つか三つ続いたら、次の段落を観測結果、次の入力、短い反問のいずれか一つに絞ってよい。
疎な段落にも、値、挙動、判断条件のどれかを含める。
余白だけを作る一行は、休符ではなく空文である。

「参照層」では、一項目の密度をそろえる。
長い背景説明を挟むより、最小例、表、関連ページへ分ける。
ただし、表を読むための定義と失敗条件は同じ項目に残す。

「規則層」では、一段落を一つの判断に限る。
規則、根拠、例が長くなる場合は、規則を独立させたあと、根拠と例を一段落ずつ置く。

具体から意味へ引く段落と、意味からコードへ戻る段落を交互に使えるのは「通読層」だけである。
「参照層」と「規則層」では、読者が途中から着地できる構造を優先する。

### ページと節の入り方

「通読層」の操作ページは、読者が終点を判定できる目標と、開始に必要な前提から入る。
概念ページは、素朴な期待と実際の型、出力、診断が食い違う具体から入ってよい。
架空の人物、書き手の告白、感情的な脇話は、その食い違いの代用品にしない。

「参照層」は、何を調べられるページかを最初の一文で限定する。
各節は定義、シグネチャー、操作名のいずれかから始める。
入口に物語的な問いを置くと、検索から来た読者が答えを探し直すことになる。

「規則層」は、選択の対象と推奨の強さから始める。
「なぜなら」だけを先に置き、読者に規則を推測させない。

節の冒頭に「この節では」を置く前に、その文を消しても対象と範囲が分かるかを見る。
分かるなら消す。
分からないなら、節の予定ではなく対象の適用範囲を書く。

### 列挙を具体へ着地させる

「通読層」の列挙は、直前か直後のコード、値、診断、トレードオフへ各項目を対応づける。
三つの性質を挙げたなら、例のどの部分がそれぞれを示すかを読者が指せるようにする。
対応が一対一でない場合は、無理に整形せず重なりを明記する。

「参照層」の構文表とAPI表は、それ自体が具体である。
表の後ろには、項目の言い換えではなく、選択条件、例外、最小例のうち必要なものだけを置く。

「規則層」の列挙は、各規則に違反例か適用場面を与える。
同じコード片が複数の規則を示す場合は、規則ごとの差分を指す。

列挙の後ろに「以上が主な点である」とだけ書かない。
新しい判断がない総括は、列挙の呼吸をもう一度止める。

### 状況と文書の話題テスト

- **状況文**：Yulangの構文、値、データ、コンパイラーの挙動、トレードオフ、診断、例の成否、読者がそこから導く具体的な推論を更新する文
- **文書文**：このページが何を述べたか、次に何を述べるか、説明が重要かどうかだけを更新する文

疎な段落や短い決め文句は、まず「状況文」か「文書文」かで判定する。
「状況文」なら、前後より密度が低くても生産的な緩みになりうる。
「文書文」なら、短く響きがよくても原則として削る。

「文書文」を残せるのは、次の四つの機能に限る。

1. 対象範囲、前提、規範の強さを定める。
2. 実際に到達でき、そこで回収される関連項目へ案内する。
3. 読者が立てる誤った命題を「」で正確に示して退ける。
4. 実行可能な例の開始条件か終了条件を示す。

「通読層」では、この四つに加えて、直後の操作が答える問いを一つだけ置ける。
「参照層」と「規則層」では、続きを読む動機を作るためだけの問いを足さない。

## 日本語に固有の追加規則

Markdownのソースでは、一つの文を一つの行に置く。
表示上の段落は空行で分け、同じ段落の文を空行なしで続ける。
表、コード、URL、引用された原文は対象外とする。

用語を本文で初めて定義するときは太字にする。
導入後にその用語自体を話題にするときは「」を使う。
単なる強調、製品名、識別子を初出という理由だけで太字にしない。

日本語の本文と見出しでは、em dash、horizontal bar、2倍ダッシュを使わない。
挿入は全角括弧に入れ、言い換えは文を分ける。
コード、書誌情報、英語の固有表記は対象外とする。

日本語の並列に中黒を使わない。
「構文、値、効果」のように読点と接続語で関係を示す。
単一の固有名詞に含まれる中黒は保つ。

用語と説明を並べる定義リストは「**用語**：説明」の形にする。
ダッシュや罫線を区切りに使わない。

命題を否定するときは、否定する内容を「」で正確に引用する。
「何も解決しないわけではない」のように、対象の分からない否定を書かない。

因果を主張する文には、結果を生む機構を一文で添える。
「キャッシュすると速くなる」だけで終えず、どの処理を再利用してどの再計算が消えるかを書く。

前方参照を書いたら、参照先の見出しと回答を実際に指せるか確かめる。
参照先が存在しても、約束した命題に答えていなければ未回収である。

「確かに」「ただし」「とはいえ」で譲歩したあとには、条件を狭めるか、判断を進める文を置く。
譲歩だけで段落を閉じない。

太字の強調は、誤読を防ぐ否定か節の帰結に限り、一節に1～2か所を上限の目安とする。
初出用語の定義と表の見出しは、この目安に数えない。

「重要なのは」で主張を予告しない。
重要なら、その主張を主語と述語で直接書く。

## 英語本文

### 英語の拍

英語では、語尾の変化ではなく文長と構文の違いで拍を作る。
短い主節のあとに条件を含む長めの文を置き、結果を短い文で止める。
三文以上がほぼ同じ語数と構文で続いたら、一文を結合するか、到達点を短く切り出す。

「通読層」では、短文を観測や転回に使える。
「参照層」では、同じ種類の情報に似た構文を使い、項目間の走査を助ける。
「規則層」では、`Use`、`Avoid`、`Do not`で選択を先に置き、理由の文だけを長くする。

### 語のレジスター

意味が同じなら、短い日常語を選ぶ。
Anglo-Saxon系の短い動詞を既定とし、ラテン語系の長い動詞は意味の区別に必要な場合だけ使う。
`use`、`start`、`end`、`help`で足りる場所に、`utilize`、`commence`、`terminate`、`facilitate`を置かない。
確立した技術用語、API名、型理論上の区別は、短い語へ崩すと精度が落ちるため原語を保つ。
ラテン語系の語は、定義済みの概念を正確に指す場合に使い、文章を重く見せる目的では使わない。

### `you`と`we`

| 層 | `you` | `we` |
| --- | --- | --- |
| 通読 | 読者が行う操作と観測する結果に使ってよい。 | 書き手と読者が同じ例から同じ推論を行う一文に限る。 |
| 参照 | 手順か、読者の選択が結果を変える条件に限る。 | 使わず、Yulang、compiler、functionなど実際の主体を書く。 |
| 規則 | 必要なら結果の受け手を示すために使うが、命令文の主語は省ける。 | 使わず、規範の主体と対象を明記する。 |

`we`をYulangの設計者、利用者、コンパイラーの曖昧な集合として使わない。
`you`を親しさの演出として足さない。

### 法助動詞

`must`は要件か論理的必然、`should`は推奨か期待される結果、`may`は許可、`might`と`can`は可能性に使う。
同じ節で`may`を許可と可能性の両方に使わない。
不確実性があるときは、法助動詞だけでぼかさず、その根拠か条件を同じ段落に置く。

「通読層」の概念説明では、素朴な推論を明示したうえで、`must`や`cannot`を含む確信を次の事実で崩してよい。
その確信が暫定的だと文脈で分からない形にはせず、直後の段落で反証する。
「参照層」と「規則層」では、あとで覆す断定を書かない。

### 冠詞と限定詞

新しく導入する可算名詞には`a`か`an`を使い、導入済みの同じ対象には`the`を使う。
種類全体を述べるときは、`Handlers can resume continuations.`のように複数形を無冠詞で使う。
Yulangのコンパイラーを一つのシステムとして指す場合は`the compiler`と書く。
`this`、`that`、`these`、`those`は、直前に一つの明確な参照先がある場合だけ使う。
`the value`のような限定句を書いたら、読者がどの値か一つに決められるか確認する。

### 断片文と句読法

文の断片は、見出し、表のセル、並列された箇条書きで使ってよい。
「通読層」の本文では、コードか診断の直後に観測を固定する断片を一つだけ置ける。
`No match.`のように省略された内容が一意に戻せることを条件とする。
「参照層」と「規則層」の本文は完全な文で書く。

独立節をコンマだけで接続するcomma spliceを使わない。
因果を示すなら接続詞、説明を導くならコロン、別々の主張ならピリオドを使う。
セミコロンは、密接に対照する二つの独立節を一文に保つ場合だけ使う。
三つ以上の独立節をセミコロンで鎖にしない。

### 空の英語表現

`It's worth noting that`と`It should be noted that`は削り、後ろの命題を主節にする。
`In this section we will`と`We are going to`は、対象か結論を直接書く。
`delve into`、`explore`、`comprehensive`、`robust`、`seamless`、`powerful`は、何をどう扱うかが増えないなら使わない。
動詞の`leverage`は`use`へ戻す。
`simply`、`just`、`easily`、`obviously`、`of course`は、読者の作業を根拠なく軽く見せるため使わない。
数量や限定として実際に意味を持つ`just one branch`まで削らない。

## 翻訳対

30組すべてで、英語ページを意味内容の正本とする。
ページごとの例外は設けない。
日本語側で事実誤認を見つけた場合は、同じ変更で英語の正本を先に、または同時に直す。

翻訳対は、見出しの階層、順序、節の数を対応させる。
各言語の見出しから生成されるslugは同じ綴りでなくてよいが、対応する節のanchorは一対一で存在させる。
明示的なanchor IDや外部から参照されるanchor IDがある場合は、同じIDを両言語に置く。
片方だけで節を分割する必要が生じたら、意味上の同じ分割を正本にも反映する。

翻訳は節と段落の役割を保ち、節内の拍を対象言語で組み直す。
英語の一節を日本語の一節へ対応させても、文や節を句単位で同じ順に移さない。
英語の短い主節が日本語で不自然なら、条件と結んで一文にする。
日本語の反問が英語で芝居がかるなら、読者が判断する条件へ書き換える。

識別子、構文、型名、モジュール名はコード表記を保つ。
自然言語の術語は、既存の翻訳対を`rg`で検索し、同じ概念に既存の対応語があればそれを使う。
対応語が定まっていない場合は、意味の近い訳語を複数作らず、原語をコード表記で保ってから用語を決める。
一つのページ内で言い換えによる変化を付けない。

問い、短文、語順による転回が片方の言語で働かない場合は、その形式ではなく機能を移す。
問いは条件へ、短文は段落の到達点へ、語順の転回は接続表現へ置き換えられる。
装置を保存するために意味、規範の強さ、適用範囲を変えない。

正本と翻訳が同じ変更でそろわない場合は、両ページのH1直後に`<!-- translation-sync: out-of-sync; source: en; checked: YYYY-MM-DD; scope: 差分の範囲 -->`を置く。
`scope`には、未同期の見出し名か命題を具体的に書く。
同期を戻した変更で、両ページのmarkerを同時に削除する。
issueやcommit messageだけに記録し、公開ソースからずれを見えなくしない。

## 草稿後の機械点検

点検は次の順で行う。

1. 層を確認し、ページ表の層と各節に適用した例外を列挙する。
2. 事実、規範の強さ、コード、診断が実装と一致するか確認する。
3. 各段落の先頭文と独立短文を「状況文」と「文書文」に分け、四つの例外に入らない「文書文」を削る。
4. 文長と構文を並べて見て、同じ拍が三文以上続く箇所と、短文が三つ以上続く箇所を直す。
5. 冒頭、疎な段落、節間の橋、列挙の着地が層の規則に合うか確認する。
6. 否定した命題、因果の機構、譲歩後の前進、前方参照の回収先を一つずつ指す。
7. 日本語では一文一行、太字の用途、「」による再言及、禁止記号、中黒、定義リストのコロンを検索する。
8. 英語では`you`と`we`、法助動詞、冠詞、断片文、comma splice、セミコロン、空の表現を検索する。
9. 翻訳対の見出し階層、anchor、コード、リンク、数値、規範の強さを節ごとに照合する。
10. 開いた問いを台帳にし、「通読層」では回収位置を指し、「参照層」と「規則層」では未回収がないことを確かめる。
11. 最後に表示を読み、コードや表から離れた抽象語、リンク切れ、言語をまたいだ用語の揺れを探す。

## 平坦な文章の症状と処方

| 症状 | 診断 | 処方 |
| --- | --- | --- |
| 全段落が同じ調子で疲れる | 文長と構文がそろいすぎている。 | 点検4を行い、条件を運ぶ文と到達点の短文を分ける。 |
| 密度を下げたのに間延びする | 疎な段落が「文書文」になっている。 | 値、挙動、判断条件へ書き換えられなければ削る。 |
| 正しいが先を読む理由がない | 「通読層」で観察すべき差が見えていない。 | 素朴な期待を壊す出力、診断、失敗例を一つ置く。 |
| 参照項目が芝居がかる | 自己完結すべき項目に問いや溜めがある。 | 定義か結論を先頭へ戻し、問いを条件に直す。 |
| 理論だけ急に冷たく見える | 抽象語が観測可能な差から離れている。 | 「通読層」なら型出力か反例を直前に置き、「参照層」なら最小例を直後に置く。 |
| 列挙が宙に浮く | 項目とコード、診断、選択条件の対応がない。 | 各項目が具体のどこに現れるかを指す。 |
| 節の冒頭が事務的に見える | 予定だけを述べ、対象を更新していない。 | 目標、適用範囲、定義、具体的な不一致のうち、その層が要求するものへ置き換える。 |
| 規則が弱く見える | 助言と禁止が同じ語調になっている。 | `should`と`must not`、「するとよい」と「してはならない」を使い分ける。 |
| 英語が生成文らしく見える | 長い語、空の予告、容易さの副詞が内容を代行している。 | 平易な動詞へ戻し、予告を削り、条件を具体化する。 |
| 翻訳だけ不自然に弾む | 原文の節と語順を句単位で写している。 | 意味と節の役割を固定し、対象言語で文長と転回を組み直す。 |
| APIページを走査しにくい | 項目ごとに情報の順番が違う。 | 概要、構文、条件、結果、失敗、例の定位置をそろえる。 |
