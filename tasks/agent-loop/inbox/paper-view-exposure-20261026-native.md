## Concrete existing equations and identity path

1. `Machine::consume` first checks `receiving.matches_value(received.view, received.value)`. It creates `receipt := receipt(current_execution_owner(), received.view, site, None)`. For `NameConsumption::Execute`, it requires `interface == Computation`. If `has_root(received.view)`, it obtains `execution := execution(received.view, receipt)`, pushes that exact execution record to `executing_views`, and pushes `Frame::RootCompReturn { execution }`; then it calls `execute_with_substitution(received.value, site, received.dispatch)`.
2. `Receiving::execution(v,r)` requires `receipts[r].view == v`; for ordinary/root-comp kinds there is no extra mapping. It allocates occurrence `n = executions.len()`, appends `(v,r)`, and returns `ExecutionView { view:v, receipt:r, occurrence:n }`. Thus the represented entry identity is exactly `(ViewHandle, ReceiptHandle, occurrence)`, tied to the `ValueHandle` through `matches_value`; it is not a paper owner/path identity `χ`.
3. `execute_with_substitution(value,site,σ)` dispatches only executable value kind. Delay substitutes its captured environment and starts `Evaluate { code, environment }`. Request composes `payload.dispatch := dispatch.then(payload.dispatch, σ)`, allocates monotonically increasing event identity, and starts `State::Request` with the same declaration/payload/source, observation list generated from all currently executing views, and an empty suffix. It does not add exposure metadata to request, payload, or continuation.
4. On normal `RootCompReturn`, the machine checks that the actual returned `(view,value)` still match, pops the top `ExecutionView`, and returns the exact `ReceivedValue` unchanged (including dispatch, interface, view). The source comment explicitly says the consumed computation root has no result-path image; it preserves actual result view/unknown coverage/private captures/dictionary and assumes no groundness. This is a concrete leave equation, but it is not the manuscript’s `result-path metadata` transfer.
5. When a request bubbles across `RootCompReturn`, `propagate_request` pops the executing view via `end_execution_view` and appends the same frame plus its original `ExecutionView` to request suffix. `capture_template` encodes it as `TemplateNode::View { inner, original }`. On each replay, that node validates/reopens `(original.view, original.receipt)` by allocating a fresh occurrence, pushes a new active execution record and a fresh `RootCompReturn`, then resumes the inner node. The historical occurrence is not replayed as the new live occurrence. This preserves machine observation lifetime/identity; it does not store or replay paper exposure remainder/path data.
6. At request creation, `Receiving::observe(event, &executing_views)` yields observations keyed by fresh observer identity and event, each retaining its `ExecutionView`. Existing request-side evidence therefore relates event -> active execution view/receipt occurrence. `Observation` contains no path, `χ`, delimiter stack payload, structural prefix or projection/adapter correspondence. `dispatch` is separate and transformed under substitution; it is not view metadata.
