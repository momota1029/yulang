## Constructor and action paths

`candidate_source.rs::emit_candidate_source` schedules a Lambda's outer `FormalEntry` at the one `Action::FormalEntry` emission site when its root annotation has an effect row, followed by `Action::FormalAnnotation` for its annotation value. `execute_candidate_graph_plan` runs definition-root schedules when candidate source is active; `execute` then runs loose and expression schedules, skipping only operator-provider expressions already executed by the provider route. All use the same synchronous schedule path. `execute_candidate_source_schedule` calls `begin_candidate_source`, then `drive_candidate_source`; `step_candidate_source` calls `execute_candidate_action` and increments the schedule cursor only after that call succeeds. The dispatch arms call `candidate_formal_entry_annotation` and `candidate_formal_annotation` directly. They are not wrapped in a route transaction. On error the schedule wrapper clears only `state.source`; `execute_candidate_graph_plan`'s error handling clears only scratch/orchestration accounting.

The separate public `solve_receiving_residual_experiment` entrypoint in `candidate_receiver.rs` constructs a local candidate session, then `execute_receiving_assembly` manually walks the two authenticated definition schedules and sends every non-special action through the same `execute_candidate_action` dispatch. Its special `Module` actions use their own route transaction, but this does not enclose adjacent `FormalEntry`/`FormalAnnotation` actions. If any action or subsequent assembly check fails, `?` returns from the public function while the local session is owned only by that stack frame, so it is dropped. On successful assembly, the function moves the session into a local `ReceivingResidualExperiment`; if `publish_authenticated_residual` then fails, `map_err(...)?` returns while that local experiment (and its session) is dropped. Only after both phases succeed is the experiment returned. The returned experiment offers read-only public outcomes; there is no public session-resume operation.

`candidate_receiver.rs` has one further `FormalEntry` occurrence in `is_authenticated_source`, which validates schedule/output correspondence and does not execute an action. Test-only direct constructors, manually wrapped `with_route_transaction` calls, and test helpers are excluded as production proof.

## Exact publication, error propagation, rollback and owner order

`candidate_formal_annotation` builds permissions and terms locally, admits the two value links, validates retained permission bytes, then transfers `permissions` into `formal_permissions` and inserts the parameter's negative term into `formal_domains`. Its fallible `sample_f4_resources(IncomingRoute)` runs after both publications; therefore a sample failure returns `Err` with these semantic fields still present. A later fallible cleanup can also fail after publication. `candidate_formal_entry_annotation` may append the concrete outer `FormalEntryPermission` after symbolic linking, then performs its fallible resource sample; its returned error also does not itself retract that record.

The schedule dispatcher propagates constructor errors with `?` before cursor advancement. It does not invoke route rollback. Candidate graph execution propagates schedule errors through `execute_candidate_graph_plan` and `execute_scc_plan`; `execute` propagates that error to its owner. The normal candidate owner is `shadow_apply::CandidateInference::solve`/its shared inner solve: it keeps `InferenceSession` in a local variable, maps `session.execute()` or `execute_candidate_field_tails` failures to `CandidateError`, and returns early. In deferred-readback branches it may copy bounded receiver/graph-count snapshots into the caller's readback object before returning `Err`, but it never returns the session or a `CandidateInference` on that path. On success `finish_candidate(self)` consumes the session into `CandidateSolvedResult`, which is then wrapped in `CandidateInference`; there is no failed session to retry. `run_candidate(self)` also consumes its session but has no non-test caller at this baseline.

Route rollback is real but not the production envelope for these source actions. `with_route_transaction` starts a route journal; on operation `Err` it calls `rollback_route_transaction`, whose intrusion undo delegates to `candidate_intrusion::State::rollback`, while the effect-state checkpoint removes inserted formal-domain keys and truncates nested and entry permission vectors. The actual source schedule path calls constructors directly with no such enclosing transaction. In the receiver assembly path only `Module` action routing is transactional; formal actions are direct. The result therefore relies on owner discard, not on a generalized rollback claim.

After successful completion, `candidate_scheme::capture_candidate_graph` reads formal domains to retain negative formal roots. `admit_lambda_fact` uses a registered domain during successful solver execution. Candidate graph `formal_effect_permissions` projects nested permissions only from a successful candidate graph and rejects an incomplete path/port projection instead of returning a partial list. These consumers are downstream of successful completion; the failed local session is unavailable to them.
