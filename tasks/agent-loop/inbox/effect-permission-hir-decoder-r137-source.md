## Parent application and source map

The actual HIR source type is `SourceAnnotationType { effects: Option<SourceEffectRow>, value: SourceAnnotationValue }`. `source_annotation.rs::parse_type_source` constructs `Int`, `Bool`, `Str`, `Variable(trimmed sigil spelling)`, `Hole(SourceNodeKey of this TypeExpression)`, `Unit` from an empty group, ordered `Tuple(Vec<...>)`, and `Function { argument, result }`. A parenthesized single unseparated item is grouping and returns that item; separated/non-single groups make a tuple. `parse_row` preserves row `SourceNodeKey`, pushes concrete resolved `SourceEffectId`s and symbolic variable spellings into separate ordered vectors, and rejects more than one symbolic variable. Repeated concrete mentions remain repeated vector entries. It resolves each concrete spelling only when the effect namespace has exactly one declaration. Recovery/malformed forms fail; source-node lookup can fail with `StructuralProjection`, and vector reservation failures with `IdentityExhausted`.

The receiver-side structural path for nested formal annotations is:

| HIR value constructor | Native equation in `candidate_effect.rs::candidate_formal_value_pair` | R136 inventory equation |
|---|---|---|
| `Unit`, `Int`, `Bool`, `Str` | positive/negative corresponding collected native leaf terms | each is a permission-free leaf |
| `Variable(name)` | scope-keyed `candidate_annotation_variable(scope,name,level)` row, then positive/negative live terms | permission-free leaf; value-variable identity is outside the permission record |
| `Hole(position)` | scope-and-SourceNodeKey-keyed `candidate_annotation_hole(scope,position,level)` row, then positive/negative live terms | permission-free leaf; hole identity remains outside the permission record |
| nonempty `Tuple(elements)` | iterate in source order, append `Element(index)` path, recursively build each child pair, construct positive and negative tuple terms in that same order; reject empty tuple or any immediate child effect row | `elementInventory` visits each child in index order and appends the same `Element(index)` path; immediate child effect rows are outside the R136 supported fragment |
| `Function { argument, result }` | visit argument value at reversed variance, result value at incoming variance, then argument effect at reversed variance, then result effect at incoming variance; construct `positive_function_term(an, qan, qrp, rp)` and `negative_function_term(ap, qap, qrn, rn)` | `inventory` appends argument subtree, result subtree, argument row emission, result row emission; path steps are `Argument`/`Result`; argument flips polarity, result preserves it |

The native formal walk starts at `Polarity::Negative`, so the R136 negative polarity corresponds to `false`. `candidate_formal_pair` first applies row support: at negative variance, only a single symbolic-only row or a concrete-only row is accepted; positive rows allow at most one symbolic variable. The native `candidate_formal_effect_port` equations are: no row -> fresh shared effect row, no grant; singleton symbolic-only row -> scope/name-memoized fresh effect row, no grant; negative concrete-only row -> fresh effect row and append one `FormalPermission`; positive row with at most one symbol -> use `candidate_signature_effect` on both sides, no `FormalPermission` emission here; other rows fail. The emitted negative concrete-only record retains parameter recipe index, occurrence, source owner, scope, exact structural path, row `SourceNodeKey`, and the concrete `SourceEffectId` sequence. This matches the *shape and order* of R136 `emit`: negative, nonempty concrete list, empty variable list, exact path/context/row record. It does not authenticate the ID encodings.

The root `annotation.ty.effects` is not a nested Function port. For a lambda parameter with any effect row, `candidate_source.rs` schedules `FormalEntry` separately from `FormalAnnotation`. `candidate_formal_entry_annotation` validates the registration/formal/source owner/scope/occurrence tuple, connects a symbolic root tail to the entry effect with two constraints, and records concrete root members as a distinct `FormalEntryPermission` carrying registration, formal, annotation position, row position and entry effect. R136 `constructEntry` models this separate outer record; it is not part of nested `inventory`. Thus root rows must not be inserted at path `[]` in the nested permission list.

Other source annotation routes are distinct: local binding annotations schedule `LocalAnnotation`; expression ascriptions schedule `Ascription`; definition/header annotations schedule `Annotation`; source operation signatures are dispatched through operation/catch actions. These use signature/local constructors, not `candidate_formal_value_pair`'s `FormalPermission` output. The packet’s R136 inventory theorem only corresponds to the nested formal-annotation constructor. A proof must not equate the broader set of annotation-bearing HIR forms with that one permission output.

The permitted source blobs do not establish whether the caller wraps every production `FormalAnnotation` action in an enclosing route transaction that restores this publication on error; the explicit transaction behavior shown by R136 historical tests is not production-path authentication.
