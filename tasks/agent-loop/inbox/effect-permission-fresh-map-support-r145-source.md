## Source trace

At the frozen baseline, source collection assigns each computation scope by appending its `EffectScopeId` to `Plan.scope_regions` and recording it in its owning region (`candidate_source.rs:155-169`). Each scoped call receives `InputRouteId(source_input)` where `source_input` is the candidate-call index, and records that ID in the call occurrence's region (`candidate_source.rs:1884-1894`). `ScopeInventory::from_plan` reconstructs per-region input ownership and initializes origin vectors; origin values record ancestry and are not an injectivity argument (`candidate_source.rs:223-245`).

`ScopeInventory::fresh(owned, caller, ...)` validates the caller and resource limits, snapshots the current lengths as allocation bases, reserves region identities, then copies every scope/input listed in the supplied owned regions. New IDs are `EffectScopeId(scope_regions.len())` and `InputRouteId(input_regions.len())` immediately before each append; the `ScopeRemap` records old-to-new entries (`candidate_source.rs:296-352`). Thus, for a successful call with the actual unique owned-region closure, the map's domain is the scopes and inputs listed in those regions, and its image is in the newly appended scope/input ID intervals. Distinct new IDs follow from those append indices and unique source IDs; equality of `scope_origins` is not used. `fresh` mutates the inventory while constructing the map, so an allocation/resource error can occur after earlier copied entries were appended; an error returns no completed map.

`prepare_candidate_fresh_use` calls `context.begin_use()` first, then invokes `ScopeInventory::fresh(graph.owned_regions, caller, ...)` before row, term, effect-view, context, or evidence reconstruction (`candidate_scheme.rs:4444-4451`). It computes one `scope_remap` for that invocation. For every distinct parent relation referenced by the captured bounds, it reads that parent's incoming `ScopedFlow`; if the flow has a transformer, it calls `ScopeTransformer::remap` using this same scope/input map, with identity fallback for IDs absent from the map. It then maps the demand's `output_scope` and `input` through the same lookups, also with identity fallback; it remaps the demand root through the one `terms` reconstruction table, and changes `use_instance` to this FreshUse's `context_use` iff the input lies in the map (`candidate_scheme.rs:4773-4800`). The resulting per-parent flow is retained in `FreshUse.scoped_relations`. Each captured bound later looks up that retained flow and supplies it to the FreshUse transport child (`candidate_scheme.rs:4861-4906`; `candidate_context.rs:4697-4710`).

Within one FreshUse, repeated bounds with the same parent reuse the same retained mapped flow; each emitted bound transport still has its own bound admission. Replay occurs later in context propagation: it composes the lower and upper transformers and carries the upper demand (`candidate_context.rs:4455-4476`). Replay does not allocate a second `ScopeRemap`. A subsequent FreshUse call begins with a new context-use identity and copies from the inventory's then-current lengths, so successful later copies use later append intervals. Captured local uses retain the returned FreshUse in their local-use frame; nested/repeated preparation calls are separate invocations (`candidate_scheme.rs:5214-5223`). The module path calls through `freshen_candidate_graph_core -> prepare_candidate_fresh_use`, then drives bounds using the returned FreshUse (`candidate_scheme.rs:4423-4443`). The local-use path is the other committed production call site (`candidate_scheme.rs:5214-5217`). Other `prepare_candidate_fresh_use` matches in that file are tests. ## First missing premise and exact source owner

The native transformer rename law requires the scope and input maps to be injective on the **combined finite support** being renamed. The source establishes local injectivity for `ScopeTransformer::remap` on the transformer-only support and rejects duplicate mapped scopes (`candidate_scope.rs:214-258`). It does not check the union of that support with the demand coordinates and other incoming-state support. `prepare_candidate_fresh_use` separately maps demand coordinates, and its `unwrap_or(id)` means an incoming identifier outside this FreshUse's `graph.owned_regions` domain is left unchanged.

No concrete collision can be concluded from committed source alone: successful IDs are allocated by append indices, while source-origin equality is only ancestry. The first unclosed source premise is the global support/allocator invariant needed to justify the identity-fallback case: every scope/input ID in the incoming transformer, demand and relevant incoming state is an already allocated ID below the pre-copy inventory length (including IDs from prior successful or failed copies), and the successful FreshUse image is fresh above that entire prior range; also, the captured `owned_regions` traversal contains each source scope/input key at most once. The source constructors strongly indicate this invariant (scope IDs are appended by `computation_scope`, input IDs are indexed from `source_input`, and copies append), but the single-boundary code does not authenticate the full union or expose a checked support certificate.
